OBJECTIVE

Build the dedicated WAVEX Send screen and recipient-entry experience.

This phase is UI + public-data preparation only.

DO NOT implement actual transaction sending, signing, broadcasting, gas estimation, transaction construction, or blockchain mutation in this phase.

The goal is to create a polished, production-quality Send screen that is ready to connect to the transaction pipeline in the next phase.

VISUAL DIRECTION

Continue the established WAVEX visual language from the attached wallet UI reference:

- dark futuristic wallet
- deep navy/black background
- cyan/electric blue/violet accents
- subtle restrained glow
- premium rounded surfaces
- clean typography
- strong visual hierarchy
- compact controls
- polished input states
- avoid excessive gradients or visual noise
- mobile-first
- feel like a serious modern self-custodial wallet, not a generic finance app

Reuse the existing theme tokens and components instead of creating a second design system.

SCREEN STRUCTURE

Create:

src/components/WalletSendScreen.tsx
src/components/WalletSendScreen.logic.ts
appropriate tests

The Send screen should include:

1. Header
- Back button
- "Send" title
- current selected network indicator

2. Asset selector
- Allow the user to choose an asset from the currently selected network
- Use the existing PortfolioReadModel / asset presentation architecture
- Initially support:
  - native asset
  - ERC-20 fungible tokens already represented by the portfolio
- Do not add new blockchain reads directly from the UI
- Do not invent balances

3. Available balance
- Display the selected asset's available balance
- Reuse existing exact formatted balance
- Clearly identify the asset symbol
- Preserve unavailable/stale/invalid states honestly

4. Recipient field
- Label: "Recipient Address"
- EVM address input
- Full address should remain editable/selectable
- Validate syntactic EVM address format locally
- Normalize/checksum where appropriate using existing utilities
- Do NOT send anything to the blockchain merely to validate an address
- Do NOT attempt to determine whether the recipient is an EOA or contract in this phase

5. Address states

Support clear visual states:

- empty
- typing
- valid
- invalid
- normalized
- cleared

Do not show "wallet verified", "safe address", "trusted address", or similar claims.

A syntactically valid address is NOT proof that the destination is safe.

6. Paste action

Provide a clear Paste action using the existing expo-clipboard boundary.

Important:
- The app may write the public recipient address to clipboard through the existing boundary.
- Do not persist clipboard contents.
- Do not log clipboard contents.
- Do not create a clipboard history.
- Do not transmit clipboard contents anywhere.

7. QR / Scan action

Add a "Scan" action in the recipient field area if it fits the existing design.

However:

DO NOT implement QR scanning in Phase 4.5.

It should remain a controlled "Coming Soon" / deferred capability.

Do not add camera permissions or camera dependencies.

8. Amount field

Add an amount input for the selected asset.

Requirements:
- decimal input appropriate for token decimals
- no negative values
- no exponent notation
- no malformed decimal values
- reject excessive decimal precision
- preserve exact user-entered value while editing
- do not convert financial amounts through floating-point arithmetic
- use the existing exact amount parsing/formatting utilities
- no hidden rounding
- no hidden fee deduction
- no automatic "max" behavior yet unless it can be implemented purely as a deterministic UI helper

9. MAX button

Add a visible MAX control.

For this phase:
- MAX should populate the selected asset's exact available balance as the amount
- Do not subtract gas automatically
- Do not estimate gas
- Do not calculate transaction fees
- For native assets, explicitly make it clear that this is the current balance, not "maximum spendable after gas"
- For ERC-20, simply use the available token balance

10. Network safety

The Send screen must always be scoped to the currently selected network.

Display the selected network clearly.

Do not allow the Send screen to silently switch networks.

If the selected network is:
- configured → normal UI
- unconfigured → controlled unavailable state
- disabled → controlled unavailable state

If the network context changes while the screen is open:
- invalidate recipient/amount draft as appropriate
- refresh the presentation state
- do not carry a draft silently across networks if that could cause ambiguity

11. Asset/network mismatch protection

A token from one network must never accidentally appear as a sendable asset on another network.

Use the existing network-scoped AssetIdentity.

Contract address + network must remain the authoritative token identity.

12. Navigation

Implement:

Home → Send
Assets → Send
Send → Home / Back

The selected asset should be able to flow into Send when the user starts Send from an asset row/detail context.

If no asset is supplied:
- default to the currently selected network's native asset where appropriate
- do not invent an asset

13. Form validation

Build UI-level validation for:

- missing recipient
- invalid recipient
- missing amount
- malformed amount
- excessive decimal precision
- zero amount
- amount greater than available balance
- unavailable asset
- unavailable network

Use clear human-readable messages.

Do NOT perform:
- balance refreshes
- gas estimation
- nonce retrieval
- transaction construction
- signing
- broadcasting

Those belong to later transaction-flow phases.

14. Continue button

Add a primary CTA such as:

"Review Transaction"

It should only become enabled when the local UI prerequisites are satisfied.

When pressed in this phase:
- do NOT build a real transaction
- do NOT estimate gas
- do NOT sign
- do NOT broadcast
- transition only to a controlled placeholder/review state indicating that transaction review will be connected in the next phase

Prefer creating a reusable draft model for the future transaction flow, containing only public/non-secret information:

- accountId
- sender public address
- networkId
- selected asset identity
- recipient
- amount
- token contract address if applicable

Do NOT include:
- mnemonic
- private key
- signing capability
- PIN
- biometric state
- SecureStore data
- encryption keys

15. Security boundary

This phase must NOT import or access:

- SecureStore
- SecureVault
- SecretManager
- KeyManager
- LocalWalletEngine secret APIs
- mnemonic data
- private keys
- WalletAuthenticator unlock APIs
- signing capability
- LocalSigner
- TransactionSigningFlow
- TransactionBroadcastEngine

Only public wallet/account/asset/network presentation data may be used.
