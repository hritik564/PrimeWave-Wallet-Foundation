DEVELOPMENT-ONLY PREVIEW TEST MODE — FIX REPLIT WEB PREVIEW ACCESS

IMPORTANT:
This is a development/testing infrastructure change only.

The Replit Web Preview is currently unusable for testing the application because it is stuck on the Wallet Locked screen.

The existing Reset Local Preview button cannot operate in the Replit web environment because native SecureStore is unavailable.

DO NOT weaken or modify the production/native wallet security architecture.

==================================================
1. OBJECTIVE
==================================================

Create a clearly isolated DEVELOPMENT-ONLY "Preview Test Mode" that allows the developer to repeatedly test the WaveX wallet application inside the Replit Web Preview.

The purpose is to make the web preview usable for:

- wallet onboarding UI
- wallet locked/unlocked UI
- 6-digit PIN flow
- account screens
- network screens
- asset/portfolio UI as it is developed
- transaction UI as it is developed
- settings UI
- general navigation and application flows

This is NOT a replacement for native security testing.

==================================================
2. CRITICAL SECURITY RULE
==================================================

There must be two clearly separated environments:

NATIVE / REAL WALLET
→ existing SecureStore-backed wallet architecture
→ real device security
→ real wallet secrets
→ real authentication
→ real signing

REPLIT WEB PREVIEW DEVELOPMENT MODE
→ development-only simulated wallet state
→ no production secrets
→ no SecureStore replacement
→ no real wallet private keys
→ no real recovery phrase
→ no real signing

DO NOT modify the native SecureStore implementation to make Web Preview work.

DO NOT introduce browser storage as the production wallet vault.

DO NOT make the production application depend on Preview Test Mode.

==================================================
3. PREVIEW TEST MODE ACTIVATION
==================================================

Preview Test Mode must only be available when the application is running in a development environment.

Use the existing __DEV__ boundary and the application's existing environment/configuration architecture.

It must NOT be possible to activate Preview Test Mode in a production build through:

- a URL parameter
- local storage manipulation
- a query parameter
- a hidden production route
- a runtime flag exposed to users
- an API call
- any user-controlled production input

Production builds must compile/run without this functionality being accessible.

==================================================
4. DO NOT USE REAL WALLET SECRETS
==================================================

The Web Preview Test Mode MUST NOT generate or persist a real BIP39 mnemonic or real private key.

Do not call the real wallet secret generation/derivation path merely to create preview test state.

Do not store:

- mnemonic
- private key
- seed
- encryption key
- PIN secret

in browser storage.

The preview wallet can use a deterministic PUBLIC test account representation for UI testing.

For example, the test environment may use a fixed, clearly documented development-only public address such as:

0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266

ONLY as a public test identity.

Do not assume or expose any corresponding private key or mnemonic.

==================================================
5. PREVIEW PIN
==================================================

The Preview Test Mode must support a developer-defined 6-digit test PIN.

The developer should be able to:

1. Reset Preview
2. Enter onboarding
3. Create/configure a test wallet
4. Set a 6-digit PIN
5. Lock wallet
6. Unlock wallet using that PIN

The preview PIN is NOT a real wallet security credential.

It must never be passed to:

- backend
- RPC
- signing engine
- SecureStore
- real wallet vault
- analytics

If persistence is needed for the preview state, use only a clearly isolated development-only preview state mechanism.

Never reuse the production wallet vault.

==================================================
6. PREVIEW RESET
==================================================

The existing "Reset Local Preview" button should be repaired/reworked so that in Web Preview it actually resets the simulated development state.

After reset, the application should return to the initial onboarding state.

Expected flow:

Reset Local Preview
→ clean onboarding
→ Create Test Wallet
→ Recovery Confirmation UI if applicable
→ Set 6-digit Test PIN
→ Wallet Home
→ Lock
→ Unlock

The reset operation must be idempotent.

If no preview state exists, reset should still succeed.

==================================================
7. DO NOT CHANGE NATIVE RESET
==================================================

The existing native reset implementation must remain intact.

On native development builds:

- SecureStore remains the wallet persistence mechanism.
- Vault deletion remains SecureStore-based.
- Authentication cleanup remains native.
- No browser fallback should be introduced.

The preview reset path and native reset path must remain clearly separated.

==================================================
8. PREVIEW STATE ARCHITECTURE
==================================================

Create a small isolated module, for example:

src/core/development/
or
src/core/dev-preview/

Use naming that makes its development-only purpose unmistakable.

Create a minimal interface such as:

PreviewTestMode
PreviewWalletState
PreviewTestStateRepository

The exact names may follow the existing architecture.

The module should support only what is needed for application preview testing:

- hasPreviewWallet
- createPreviewWallet
- setPreviewPin
- verifyPreviewPin
- lockPreviewWallet
- unlockPreviewWallet
- resetPreviewWallet

Do not expose real wallet secrets.

Do not create a second production wallet engine.

==================================================
9. PREVIEW PERSISTENCE
==================================================

If persistence is required so that a browser refresh does not immediately lose the test state, use a development-only browser mechanism inside the isolated Preview Test Mode module.

This is the ONLY context where browser persistence may be used.

It must be impossible for this repository to be imported or used by production wallet security code.

Do NOT call it:

SecureVault
WalletVault
WalletStorage
KeyStore
SecureStorage

Use an unmistakably development-only name.

Do not store sensitive secrets.

The preview PIN may be represented only as a development-test state value if necessary, but never use the production PIN storage format or production authentication storage.

==================================================
10. REAL WALLET ENGINE BOUNDARY
==================================================

Do not modify:

- LocalWalletEngine secret handling
- SecureVault
- SecureStore integration
- KeyManager
- SecretManager
- LocalSigner
- WalletAuthenticator native behavior
- transaction signing
- transaction authorization
- broadcasting

The preview layer must sit ABOVE the real wallet security boundary and must not replace it.

==================================================
11. SIGNING SAFETY
==================================================

Preview Test Mode must NOT provide a real signing capability.

Do not create:

- fake private-key signing
- deterministic private key
- development mnemonic
- browser transaction signer
- signing bypass

If future UI needs to display a signed/broadcast transaction state during UI development, create a separate clearly mocked UI fixture later.

Do not implement that now.

Make it obvious that this is a development test environment.

"Reset Local Preview"

"Development-only test wallet"

Do not expose this UI in production.

Do not redesign the application's main UI.

==================================================

Do not route the preview unlock through native biometric APIs.

If the preview UI currently attempts native biometric authentication, the preview environment should use the development PIN path instead.

This must NOT change native iOS/Android biometric behavior.
