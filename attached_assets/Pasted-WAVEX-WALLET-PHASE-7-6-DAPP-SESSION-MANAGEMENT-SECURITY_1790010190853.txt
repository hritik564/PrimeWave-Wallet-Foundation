==================================================
7. SESSION EXPIRY
==================================================

Handle expired sessions safely.

When a session expires:

- mark it expired
- prevent new requests
- invalidate pending requests
- remove/revoke through the provider adapter where appropriate
- update the UI
- do not silently reconnect

Do not automatically extend a session without explicit provider protocol support.

Do not silently recreate a session.

==================================================
8. ACCOUNT CHANGE HARDENING
==================================================

WaveX may support multiple wallet accounts.

If the active account changes:

Existing DApp sessions MUST NOT silently switch accounts.

For every active session:

- determine whether the session account still exists
- determine whether it remains the active/authorized context
- invalidate or require explicit reauthorization where appropriate

Pending requests must be invalidated if their account context no longer matches.

A DApp must never receive a signature from an account different from the one it requested.

Do not automatically rebind sessions.

==================================================
9. NETWORK CHANGE HARDENING
==================================================

If the WaveX active network changes:

Do NOT silently alter the DApp session's approved chain.

For sessions:

- retain their approved network scope
- detect whether the requested operation remains valid
- reject/defer requests targeting unauthorized chains
- invalidate stale request context

Do not automatically send a chain-switch request merely because the user changed WaveX's active network.

Do not implement automatic network switching.

==================================================
10. PENDING REQUEST MANAGER
==================================================

Create or consolidate a bounded pending-request manager.

It must track requests from:

- message signing
- typed-data signing
- transaction requests

Each request must be bound to:

- request ID
- session ID
- DApp identity
- account
- network
- method
- creation time
- expiry
- lifecycle status

Statuses should distinguish:

- pending
- reviewing
- authenticating
- signing
- broadcasting
- completed
- rejected
- expired
- stale
- failed
- cancelled

Prevent duplicate request IDs.

Prevent the same request from being processed twice.

==================================================
11. PENDING REQUEST CLEANUP
==================================================

When a session is disconnected/revoked/expired:

all pending requests for that session must become invalid.

They must NOT:

- sign
- broadcast
- return successful responses

User-facing state should explain that the request is no longer valid.

Provider responses must use appropriate rejection/error semantics.

==================================================
12. CONCURRENCY
==================================================

Ensure only one sensitive signing/execution flow is active for a given wallet security context.

Protect against:

- double tapping Sign
- double tapping Confirm Transaction
- repeated provider events
- duplicate request IDs
- concurrent authentication
- concurrent signing
- concurrent broadcast
- duplicate provider responses

Use deterministic request locking/idempotency.

Do not create unsafe global locks that prevent unrelated read-only DApp operations.

==================================================
13. TRANSPORT LIFECYCLE
==================================================

Harden the provider transport lifecycle.

Handle:

- initialized
- connected
- pairing
- session proposal
- session established
- session updated
- session deleted
- transport disconnected
- transport reconnect
- provider error

The WaveX DApp core must remain provider-neutral.

Only the provider adapter should know provider-specific transport details.

==================================================
14. PROVIDER RECONNECTION
==================================================

If the provider transport temporarily disconnects:

- do not automatically approve requests
- do not sign anything
- do not broadcast anything
- preserve safe public session metadata only where appropriate
- restore provider connectivity only according to the provider SDK's documented lifecycle

Do not invent a custom reconnection protocol.

If provider state cannot be safely restored:

fail closed.

==================================================
15. BACKGROUND / FOREGROUND
==================================================

Integrate safely with the existing AppState security architecture.

When the app backgrounds:

- sensitive pending signing/execution flows must remain protected
- no request may be auto-approved
- no request may auto-sign
- no transaction may auto-broadcast solely because the app resumes

When returning to foreground:

- revalidate pending request/session/account/network context
- expired or stale requests must remain invalid

Do NOT regress the existing wallet AppState authentication/locking protections.

==================================================
16. DAPP SESSION STORAGE
==================================================

Continue using the existing DApp session repository architecture.

Do NOT introduce arbitrary AsyncStorage/localStorage.

If the provider SDK maintains its own session state:

- keep it within the provider adapter boundary
- do not duplicate provider session persistence unnecessarily
- do not store secrets
- do not store private keys
- do not store recovery phrases
- do not store PINs

Document what is stored and where.

If a provider session cannot be safely persisted:

fail closed rather than inventing storage.
