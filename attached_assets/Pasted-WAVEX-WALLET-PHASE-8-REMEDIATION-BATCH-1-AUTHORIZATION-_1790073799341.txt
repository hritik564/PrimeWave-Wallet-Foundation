AUTHORIZATION + NOTIFICATION SECURITY

IMPORTANT:
This task is remediation of findings from the completed Phase 8 Consolidated Security Review.

Implement ONLY the findings explicitly listed in this prompt.

Do NOT:
- start Phase 9
- redesign unrelated backend architecture
- modify mobile wallet cryptography
- modify wallet signing/broadcasting

==================================================
1. SOURCE OF TRUTH
==================================================

The Phase 8 security review identified:

HIGH:
H-01 — Account authentication and wallet-ownership enforcement are absent.

H-02 — Notification registration can bind an attacker-controlled push token to an arbitrary wallet scope.

MEDIUM:
M-03 — Notification quotas are vulnerable to concurrent overrun.

LOW/INFO:
L-03 — Notification event source authorization is implicit.

The review specifically states that the existing authentication boundary is deferred and currently returns null.

The objective of this remediation is to establish a proper authorization boundary WITHOUT compromising WaveX's strictly non-custodial architecture.

==================================================
2. NON-CUSTODIAL SECURITY INVARIANT
==================================================

This invariant must remain absolute:

"WaveX Wallet must be strictly non-custodial. Private keys and recovery phrases must never leave the user's device and must never be transmitted to, stored by, logged by, or recoverable through WaveX/PrimeWave backend infrastructure."

Therefore:

NEVER send:
- seed phrase
- mnemonic
- private key
- raw wallet secret
- wallet PIN
- SecureStore contents
- vault key
- signing capability
- raw signed transaction

to the backend for authentication.

Authentication MUST NOT depend on backend custody of wallet secrets.

==================================================
3. AUTHENTICATION ARCHITECTURE — DO NOT INVENT UNSAFELY
==================================================

First inspect the existing:

- auth-boundary.ts
- route architecture
- mobile wallet/account architecture
- existing cryptographic primitives already available
- existing public account/address models
- existing signing/authentication boundaries

Determine the smallest secure architecture that can prove wallet/account ownership without transmitting wallet secrets.

The backend authorization model must distinguish:

1. Public wallet address
2. Authenticated principal
3. Authorized wallet/account scope

A caller-provided:

accountAddress
networkId
chainId

MUST NOT by itself constitute ownership proof.

Do not simply add a boolean such as:

isAuthenticated: true

Do not trust a client-supplied userId.

Do not trust a client-supplied accountAddress.

Do not use wallet address as an authentication credential.

Do not use a private key or seed phrase on the server.

If the existing architecture already contains a suitable cryptographic proof mechanism, use it.

If a secure wallet-ownership proof mechanism is NOT already present and implementing one would require a new protocol decision, DO NOT invent a production authentication protocol.

Instead:

- preserve the existing deferred auth interface
- create the correct authorization interfaces/boundaries
- add explicit fail-closed behavior for account-scoped routes
- document the exact remaining authentication dependency
- add tests proving unauthenticated access is rejected

In that case report the remaining architectural dependency clearly.

Security is more important than completing a fake authentication implementation.

==================================================
5. AUTHORIZATION RULE
==================================================

For every account-scoped request:

The authenticated principal must be explicitly authorized for the requested wallet account scope.

Requested:

networkId
chainId
accountAddress

must be checked against the authenticated principal.

Reject:

- missing authentication
- invalid authentication
- expired authentication
- malformed authentication
- mismatched account
- mismatched network
- mismatched chain
- unauthorized registration ID
- unauthorized notification scope

Use fail-closed behavior.

Never silently fall back to public access.

Never infer authorization from the public nature of a blockchain address.

==================================================
6. ACCOUNT ADDRESS NORMALIZATION
==================================================

Continue using the existing canonical EVM address normalization.

Authorization comparisons must operate on the canonical representation.

Do not create a second incompatible address normalization system.

Verify:

- checksum/canonical normalization
- case-insensitive equivalence where appropriate
- chain/network scope
- account identity

Tests must include equivalent EVM address casing.

==================================================
7. SYNCHRONIZATION SECURITY
==================================================

For:

- status
- activity
- reconciliation
- checkpoint

verify authorization BEFORE account-scoped database work.

An unauthorized caller must not be able to:

- enumerate arbitrary account activity
- read synchronization state
- read reconciliation records
- create or alter checkpoints
- cause account-scoped persistence work

Do not remove the existing:

- pagination bounds
- block-range bounds
- chain validation
- account normalization
- reconciliation protections

Authorization is an additional boundary.

==================================================
8. NOTIFICATION DEVICE REGISTRATION
==================================================

This is HIGH priority.

A caller must not be able to register:

their push token

against:

another user's wallet address.

The authenticated principal must authorize the complete:

network
chain
account

scope before device registration.

The registration must not accept arbitrary ownership claims from the request body.

Push token handling must remain private.

Push tokens must:

- never appear in public response models
- never appear in logs
- never appear in analytics
- never appear in error messages
- never be used as wallet identity
- never be returned by GET endpoints

==================================================
9. NOTIFICATION DEVICE DELETION
==================================================

Deletion must be ownership-scoped.

A caller must not be able to delete another user's device registration merely by knowing:

registrationId

or:

accountAddress.

Verify that the authenticated principal owns the registration scope before deletion.

Prefer deriving authorization from the stored registration record rather than trusting a caller-supplied account scope.

Reject cross-account deletion.

==================================================
10. NOTIFICATION PREFERENCES
==================================================

GET and PUT notification preferences must be principal-scoped.

A caller must not be able to:

- read another account's preferences
- modify another account's preferences

The account scope must come from the authenticated authorization context.

If the request also supplies an account address, it must match the authorized scope.

Never allow request data to override authenticated identity.

==================================================
11. NOTIFICATION EVENT SOURCE AUTHORIZATION
==================================================

Address finding L-03.

Inspect:

NotificationService.createEvent

and its callers.

The event creation boundary must only be callable by approved internal notification-producing components.

Do not expose a public endpoint for arbitrary notification event creation.

Use the smallest safe internal authorization mechanism.

At minimum:

- separate public request DTOs from internal event commands
- ensure arbitrary external requests cannot directly invoke internal notification-event creation
- validate that the event source is an approved internal component
- preserve existing account/network/chain validation
- preserve deduplication
- preserve bounded event fields

Do not create a client-controlled `source` string and treat that as proof.

==================================================
12. NOTIFICATION QUOTA CONCURRENCY
==================================================

Fix M-03.

Current vulnerable patterns:

- device quota check → write
- pending-delivery quota check → write

These must become concurrency-safe.

Do NOT merely increase limits.

Do NOT rely only on application-level check-then-write.

Use the existing PostgreSQL/Drizzle architecture where appropriate.

The resulting implementation must guarantee configured bounds under concurrent requests.

At minimum test concurrent attempts that exceed:

maxDevicesPerScope

and:

maxPendingDeliveries

Expected result:

The configured quota must not be exceeded because of race conditions.

Preserve existing uniqueness constraints and deduplication.

==================================================
13. PUSH TOKEN STORAGE
==================================================

Address the security concern identified in M-02 without inventing unnecessary cryptography.

Inspect current notification token storage.

The backend may need to retain push tokens for actual future delivery, but they must remain protected.

Implement/document the smallest appropriate deployment-level protection.

At minimum verify:

- token column is never returned by public APIs
- token never appears in logs
- token never appears in analytics
- token never appears in error responses
- token is only accessible to the notification delivery boundary
- notification delivery code does not expose token values through provider errors

If database-level encryption or application-level encryption requires a key-management architecture that does not currently exist, DO NOT invent one.

Instead:
- preserve the current storage requirement
- add explicit security-boundary documentation
- ensure access is limited to the notification subsystem
- clearly document encryption-at-rest as a deployment/security requirement
- report it as a remaining operational security dependency

Do not store a second plaintext copy.
