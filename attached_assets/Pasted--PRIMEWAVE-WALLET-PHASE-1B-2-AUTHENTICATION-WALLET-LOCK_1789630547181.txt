# PRIMEWAVE WALLET — PHASE 1B-2

## AUTHENTICATION, WALLET LOCKING & RECOVERY UX

Phase 1A and Phase 1B-1 have been completed and approved.

Continue from the existing PrimeWave Wallet project.

This is **PHASE 1B-2 ONLY**.

We are now implementing the authentication and wallet-access layer around the secure local vault.

The wallet remains strictly non-custodial.

Do NOT implement blockchain connectivity, RPC, transactions, signing, swaps, DApps, WalletConnect, backend services, or portfolio functionality.

# 2. SECURITY MODEL

The wallet remains strictly non-custodial.

Never transmit or store remotely:

* recovery phrase
* mnemonic
* private key
* seed
* PIN
* password
* biometric credentials
* encryption keys

No backend should be introduced.

No network requests should be introduced.

---

# 3. AUTHENTICATION ARCHITECTURE

Implement a dedicated authentication layer under:

src/core/security/

Use the Phase 0B contracts where appropriate.

Conceptually:

AuthenticationManager

Responsibilities:

* configure authentication
* authenticate user
* lock wallet
* unlock wallet
* check lock state
* determine available authentication methods
* handle authentication failure
* handle biometric availability

The UI must communicate with AuthenticationManager rather than directly calling SecureStore.

---

# 4. PIN

Implement a wallet PIN.

Requirements:

* PIN must never be stored as plaintext.
* PIN must never be logged.
* PIN must never be sent to a server.
* PIN must never appear in analytics.
* PIN must not be stored in React state longer than necessary.
* Failed attempts must be handled safely.
* Authentication errors must be sanitized.

Do NOT invent a password/PIN hashing algorithm.

Use an established cryptographic mechanism appropriate for the chosen architecture.

If a PIN-derived key is required, use a well-established password-based key derivation function and document:

* algorithm
* parameters
* salt handling
* versioning
* migration strategy

Do NOT write custom cryptography.

---

# 5. PIN SETUP UX

Create:

SET UP WALLET PIN

Enter PIN

Confirm PIN

Then:

PIN successfully configured.

Minimum PIN length should be selected based on security/usability considerations and documented.

Do not use an easily guessable fixed development PIN.

Do not provide a hidden developer PIN.

Do not provide a bypass PIN.

---

# 6. PIN AUTHENTICATION

Create:

UNLOCK PRIMEWAVE WALLET

Enter PIN

Authentication succeeds

↓

Wallet unlocks.

Authentication fails

↓

Remain locked.

Do not reveal whether any internal secret exists based on detailed error messages.

Do not expose cryptographic details.

---

# 7. BIOMETRIC AUTHENTICATION

Implement platform-appropriate biometric authentication using established Expo/React Native APIs.

Support:

* Face ID where available
* Touch ID where available
* Android biometric authentication where supported

Do not store biometric data.

PrimeWave Wallet should use the operating system's biometric authentication mechanism.

The application must never receive raw biometric information.

---

# 8. BIOMETRIC FALLBACK

If biometrics are:

* unavailable
* not enrolled
* temporarily unavailable
* rejected
* cancelled

the user must be able to authenticate using the configured wallet PIN.

Do not lock users permanently because biometric authentication is unavailable.

---

# 9. BIOMETRIC ENABLE/DISABLE

Provide a security setting:

Biometric Unlock

ON / OFF

When enabling:

Authenticate using the current wallet authentication method.

When disabling:

Require wallet authentication.

Do not allow an unauthenticated user to change this setting.

# 10. WALLET LOCK STATE

Implement explicit wallet states:

LOCKED
UNLOCKING
UNLOCKED
AUTHENTICATION_FAILED
AUTHENTICATION_UNAVAILABLE

Keep the state machine simple and deterministic.

Sensitive wallet operations must not be available while LOCKED.

---

# 11. APPLICATION BACKGROUNDING

When the application moves into the background, implement configurable wallet locking.

The architecture should support:

* immediate lock
* short timeout
* configurable timeout

For initial production behavior, use a secure default.

When the wallet is locked:

* sensitive screens must no longer remain visible
* sensitive wallet state should not remain exposed in the UI
* returning to the application should require authentication when the configured lock policy says so

Do not claim that JavaScript memory is guaranteed to be wiped.

---

# 12. BACKGROUND SCREEN PRIVACY

Implement a privacy overlay when the application enters the background if technically appropriate.

The application switcher should not expose:

* recovery phrases
* private keys
* transaction confirmation details
* sensitive wallet information

Use platform-appropriate screen protection where supported.

Document platform limitations.

# 14. RECOVERY PHRASE DISPLAY

When displaying the recovery phrase:

* use a dedicated secure screen
* prevent accidental exposure where technically possible
* do not log the phrase
* do not send it anywhere
* do not include it in analytics
* do not put it into URLs
* do not store it in normal application storage
* do not automatically copy it
* do not automatically share it

Provide a clear warning:

> Anyone who has your recovery phrase can control your wallet. PrimeWave cannot recover your wallet if you lose your recovery phrase.

---

# 15. RECOVERY PHRASE CONFIRMATION

Do NOT simply provide a "Done" button.

Require the user to demonstrate that they backed up the recovery phrase.

For example:

Ask the user to select specific words by position.

Example:

Word #4
Word #9
Word #12

The exact implementation is up to you.

Do not expose the entire recovery phrase again unnecessarily.

Only after successful confirmation should wallet setup continue.

* do not log it
* do not persist it before successful import

* do not put it in analytics

* use the existing WalletEngine

Do not tell the user unnecessary cryptographic details.

# 23. MULTIPLE ACCOUNTS

The existing HD wallet architecture supports multiple EVM accounts.

Authentication should unlock the wallet vault as a whole.

Do not create separate PINs for each EVM account.

Do not create separate recovery phrases for accounts belonging to the same HD wallet.

---

# 24. SECRET-SAFE STATE MANAGEMENT

Do NOT store raw:

* mnemonic
* private key
* seed
* PIN
* decrypted vault

inside:

* Redux
* Zustand
* React Context
* persistent state
* AsyncStorage
* localStorage

UI state should contain only what is required to render the current screen.

Public wallet information such as addresses may be held in normal UI state.

# 25. CLIPBOARD

Recovery phrases must not be automatically copied.

If the user explicitly copies sensitive data:

* show a warning

* clear the clipboard when technically possible
* never log clipboard contents

# 26. LOGGING

Continue using SecureLogger.

Never log:

* PIN
* recovery phrase
* private key
* seed
* encryption key
* decrypted vault
* biometric information

Safe logs may include:

* authentication method
* lock state
* operation success/failure
* vault availability

---

# 27. AUTHENTICATION FAILURE

Handle:

* incorrect PIN
* cancelled biometric authentication
* unavailable biometric hardware
* locked-out biometric state
* secure-storage failure
* corrupted vault

without exposing secret material.

Do not create an infinite rapid PIN-attempt loop.

Implement reasonable rate limiting/backoff for repeated failed PIN attempts where appropriate.

Document the behavior.

Do not create a permanent lockout that could destroy access to a valid wallet.

The recovery phrase remains the ultimate recovery mechanism.
