# PRIMEWAVE WALLET — PHASE 0B

## SECURITY ARCHITECTURE, TRUST BOUNDARIES & INTERFACES

Phase 0A has been completed and approved.

Continue from the existing PrimeWave Wallet project.

This is **PHASE 0B ONLY**.

Do not implement actual wallet generation, seed phrase generation, private-key generation, transaction signing, or blockchain transactions yet.

The purpose of this phase is to design and document the security architecture and create the interfaces/contracts that Phase 1 and Phase 2 will implement.

Do not skip ahead.

---

# 1. NON-CUSTODIAL SECURITY MODEL

PrimeWave Wallet is STRICTLY NON-CUSTODIAL.

The user controls their wallet keys.

PrimeWave infrastructure must never have access to the user's private keys or recovery phrase.

The following information must NEVER leave the user's device:

* seed phrase / mnemonic
* private key
* derived private signing key
* wallet encryption key
* wallet password
* wallet PIN
* biometric credentials
* decrypted wallet vault
* raw cryptographic secrets

These values must never be:

* sent to an API
* stored in PostgreSQL
* stored in cloud storage
* written to logs
* written to analytics
* sent to crash-reporting systems
* included in error messages
* included in telemetry
* included in URLs
* included in query parameters
* included in application analytics events

This rule must be documented as a permanent architectural invariant.

# 4. CREATE SECURITY INTERFACES

Create TypeScript interfaces/contracts only.

Do NOT implement the cryptographic functionality yet.

Create a security module under:

src/core/security/

The architecture should include concepts equivalent to:

SecureVault

Responsibilities:

* save encrypted wallet state
* retrieve encrypted wallet state
* delete wallet state
* check whether a vault exists

The implementation must eventually use platform-secure storage.

Do NOT implement the storage mechanism yet.

---

WalletAuthenticator

Responsibilities:

* configure PIN authentication
* authenticate with PIN
* authenticate with biometrics
* determine biometric availability
* lock the wallet
* unlock the wallet

Do NOT implement actual PIN or biometric handling yet.

---

SecretManager

Responsibilities:

* create protected secret material
* access protected secret material
* clear secret material from memory when possible

Do NOT implement actual secret generation yet.

---

KeyManager

Responsibilities:

* derive wallet accounts
* access signing capability
* sign transactions locally

IMPORTANT:

The interface must NOT expose private keys to UI components.

Do not create methods such as:

getPrivateKey()

exportPrivateKeyToFrontend()

sendPrivateKey()

or equivalent unsafe APIs.

The future implementation should encapsulate private keys.

# 7. TRANSACTION CONFIRMATION RULE

Document this security requirement:

No blockchain transaction may be signed without explicit user confirmation.

Before signing, the user must eventually be shown relevant transaction information such as:

* asset
* amount
* destination
* network
* network fee
* total amount
* transaction type

For smart-contract interactions, the wallet should eventually provide as much human-readable information as safely possible.

The user must have:

Approve

and

Reject

options.

No automatic signing.

No silent signing.

No background signing.

# 9. CLIPBOARD SECURITY

Document the future clipboard policy.

Recovery phrases and private keys are extremely sensitive.

The architecture should support:

* explicit warning before copying sensitive information
* minimal clipboard exposure
* clearing sensitive clipboard contents when technically possible
* never automatically copying seed phrases
* never logging clipboard contents
* never reading clipboard contents unnecessarily

Do not implement seed phrase functionality yet.

---

# 10. LOGGING SECURITY

Create a safe logging abstraction.

All future application logging must go through a centralized logger.

Create something conceptually equivalent to:

SecureLogger

It must support:

* debug
* info
* warning
* error

But it must NEVER log:

* seed phrases
* private keys
* PINs
* passwords
* encryption keys
* decrypted vaults
* authentication secrets

Add documentation and safeguards to prevent accidental secret logging.

Avoid logging complete transaction payloads if they could contain sensitive user information.

---

# 11. ERROR HANDLING

Create a security-safe error architecture.

Errors shown to users should not expose:

* private keys
* seed phrases
* internal cryptographic material
* authentication secrets
* secure-storage contents

Internal errors should be sanitized before logging.

Do not include secret material in error objects.

---

# 12. MEMORY HANDLING

Document that cryptographic secrets should have the shortest practical lifetime in application memory.

Where the chosen platform/library allows it:

* minimize secret copies
* clear sensitive buffers when possible
* avoid storing secrets in global state
* avoid storing secrets in Redux/Zustand or other persistent UI state
* avoid React state for raw cryptographic secrets
* never put secrets into URL parameters

Do not claim that JavaScript garbage collection provides guaranteed secure memory wiping.

Document this limitation honestly.

---

# 13. BACKUP AND RECOVERY MODEL

Document the future recovery architecture.

The recovery phrase is the user's ultimate recovery mechanism.

PrimeWave must NOT provide server-side recovery of a non-custodial wallet.

Do not implement recovery now.

Document:

Create wallet

↓

Display recovery phrase securely

↓

User backs it up offline

↓

User verifies backup

↓

Encrypted local wallet vault created

If the user loses the recovery phrase and loses access to their wallet, PrimeWave cannot recover the wallet for them.

This limitation must eventually be communicated clearly to users.
