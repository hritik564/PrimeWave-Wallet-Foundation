2. M-01 — RATE LIMITER HARDENING
==================================================

Current issue:

MemoryRateLimiter has unbounded key growth and is process-local.

Implement a bounded in-memory limiter suitable for the current single-process development/runtime architecture.

Requirements:

- bound the number of retained rate-limit keys
- remove expired buckets
- prevent attacker-controlled unique keys from causing unbounded memory growth
- preserve existing rate-limit behavior
- fail safely if capacity is exhausted
- do not weaken limits to solve the issue
- do not trust arbitrary forwarded IP headers unless there is an explicit trusted-proxy configuration
- document that the in-memory limiter is process-local
- document that production multi-instance deployments require a shared limiter

Do NOT build a Redis dependency or external rate-limit service in this batch.

If an eviction policy is needed, make it deterministic and bounded.

Add tests for:

1. normal rate limiting
2. expired bucket cleanup
3. maximum key capacity
4. unique-key flooding
5. concurrent access
6. no unbounded map growth
7. fail-safe behavior at capacity

Preserve Batch 1 authorization behavior.

4. M-05 — ANALYTICS RETENTION CLEANUP
==================================================

Current issue:

Analytics records have expiry timestamps, but no operationally guaranteed cleanup invocation exists.

Implement the smallest safe solution.

Requirements:

- expired analytics records must be cleaned up through a bounded operation
- cleanup must not block wallet operations
- cleanup must not create an unbounded database scan
- cleanup must be safe under concurrent execution
- cleanup should be idempotent
- cleanup should operate separately for events/errors/performance where appropriate
- preserve configured retention values

If a production scheduler is not part of the existing architecture, DO NOT introduce an external scheduler/service in this batch.

Instead implement:

- a bounded cleanup entry point
- safe invocation integration where appropriate (for example controlled startup/maintenance invocation)
- clear operational documentation explaining how production should schedule it

Do not claim "guaranteed automatic cleanup" unless there is actually a reliable production invocation mechanism.

Add tests proving:

- expired rows are removed
- non-expired rows remain
- cleanup is bounded
- repeated cleanup is safe
- concurrent cleanup is safe

6. M-07 — RPC RESPONSE BYTE LIMIT
==================================================

Current issue:

The server indexing RPC client reads the complete response body before JSON parsing.

Add a hard response-body byte limit BEFORE full JSON parsing.

Requirements:

- enforce the limit while reading the response
- do not call response.text() without a bound
- abort/reject when the byte limit is exceeded
- use a deterministic configured maximum
- keep the limit appropriate for the existing bounded indexing operations
- preserve normal block/log/transaction responses
- sanitize the resulting error
- do not expose provider credentials or full RPC URLs

Add tests for:

1. response below limit succeeds
2. response exactly at/near limit behaves deterministically
3. oversized response is rejected before JSON parsing
4. malformed response remains safely rejected
5. provider/network failure remains sanitized
6. existing indexing behavior remains intact

Do not allow request parameters to influence the maximum response size.
