IMPORTANT:

This phase connects the approved transaction-review confirmation checkpoint to secure local authentication and signing.

DO NOT implement broadcasting in this phase.

The final output of this phase is a locally signed transaction.

The signed transaction must STOP before any broadcast occurs.

==================================================
1. OBJECTIVE
==================================================

Implement the secure execution step:

Review
  ↓
Confirm Transaction
  ↓
Authenticate wallet
  ↓
Authorize exact transaction
  ↓
Local signing
  ↓
SignedTransaction
  ↓
STOP

There must be NO:

- eth_sendRawTransaction
- broadcasting
- transaction submission
- automatic retry
- background sending

==================================================
2. USE EXISTING SECURITY ARCHITECTURE
==================================================

Do NOT create a second wallet/signing system.

Reuse the existing:

- WalletAuthenticator
- SecureVault
- LocalWalletEngine
- TransactionSigningFlow
- LocalSigner
- Phase 2.6 signing authorization model

Do not duplicate cryptographic logic.

Do not introduce another mnemonic derivation implementation.

Do not introduce another private-key storage mechanism.

Do not introduce another PIN system.

==================================================
3. TRANSACTION BINDING
==================================================

The signing authorization MUST be cryptographically/structurally bound to the exact transaction reviewed by the user.

Bind authorization to:

- accountId
- sender address
- networkId
- chainId
- transaction type
- recipient
- value
- calldata
- nonce
- gas limit
- fee model
- fee fields
- canonical unsigned transaction digest

The signing step must refuse to proceed if any of these values differ from the reviewed transaction.

Do not silently rebuild a different transaction after confirmation.

If reconstruction is required because of stale blockchain state:

- invalidate the previous review
- return the user to review
- require explicit re-review

==================================================
4. AUTHENTICATION
==================================================

After the user confirms the reviewed transaction:

Request wallet authentication using the existing WalletAuthenticator.

Supported authentication:

- existing wallet PIN
- existing biometric authentication where supported

Do NOT invent another authentication flow.

The authentication must establish explicit authorization for this transaction.

Authentication of the wallet alone is NOT sufficient.

The resulting signing authorization must also be bound to the exact transaction digest.

==================================================
5. BIOMETRIC BEHAVIOR
==================================================

Reuse the existing biometric architecture and timeout/error handling.

Remember:

- Expo Go cannot fully validate native iOS Face ID behavior
- development builds are required for native biometric testing

Do not weaken the security boundary merely to make browser Preview work.

If biometrics are unavailable:

- use the existing PIN fallback where configured

If authentication fails:

- do not sign
- do not retry silently
- return a sanitized authentication error

If the native biometric operation times out:

- return a controlled authentication failure
- never leave the UI stuck in an "unlocking" state

==================================================
6. PRE-SIGNING VALIDATION
==================================================

Before signing:

Revalidate:

- account
- sender
- network
- active network
- chain ID
- recipient
- asset identity
- amount
- nonce
- gas
- fee fields
- canonical unsigned transaction digest

The wallet must never sign a transaction different from the one explicitly reviewed.

If any mismatch occurs:

STOP.

Require a fresh review.

==================================================
7. LOCAL SIGNING
==================================================

Use the existing Phase 2.6 LocalSigner / TransactionSigningFlow.

The private key must remain entirely within the local wallet security boundary.

The mnemonic/private key must NEVER:

- enter React component state
- enter UI props
- enter navigation params
- enter Redux/context/global state
- enter logs
- enter analytics
- enter API requests
- enter backend requests
- enter persistent application storage outside the approved SecureVault
- be returned to the UI

The signing result should expose only public transaction information, for example:

- signed raw transaction
- transaction hash
- sender address
- network ID
- chain ID
- transaction type

Do not expose the private key.

==================================================
8. SECRET LIFECYCLE
==================================================

Follow the existing best-effort secret lifecycle controls.

Temporary derived-account/private-key references must be released after signing.

Do not retain signing material longer than required.

Do not cache signing material.

Do not persist signing material.

Do not put secret material into error objects.

Document the existing JavaScript memory limitation honestly:

JavaScript cannot guarantee cryptographic memory zeroization.

Do not claim guaranteed memory wiping if the runtime cannot guarantee it.

==================================================
9. ONE-TIME SIGNING AUTHORIZATION
==================================================

The signing capability must be:

- opaque
- one-time
- transaction-bound
- account-bound
- digest-bound

It must not be reusable for another transaction.

After successful signing:

- invalidate/release the authorization capability

After failed signing:

- release/invalidate it where appropriate

Concurrent signing attempts for the same account must be rejected according to the existing Phase 2.6 architecture.

==================================================
10. SIGNED TRANSACTION VALIDATION
==================================================

After signing:

Validate the signed result using the existing Phase 2.6 validation.

Verify:

- transaction decodes correctly
- sender recovery matches expected sender
- transaction fields correspond to the authorized unsigned transaction
- transaction hash is deterministically produced
- signature is valid

If validation fails:

- do not broadcast
- do not retry signing automatically
- return sanitized error
