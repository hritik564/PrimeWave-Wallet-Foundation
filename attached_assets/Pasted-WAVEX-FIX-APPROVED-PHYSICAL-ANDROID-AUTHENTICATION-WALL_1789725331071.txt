WAVEX — FIX APPROVED
PHYSICAL ANDROID AUTHENTICATION → WALLET RESTORATION APPSTATE RACE

The diagnostic is approved.

Implement ONLY the smallest safe fix for the identified native Android authentication/restoration race.

ROOT CAUSE CONFIRMED:

The authentication itself succeeds.

The failure is a race between:

authentication
→ wallet restoration
→ stable unlocked state

and the global AppState background/inactive auto-lock path.

The existing protection only covers biometricPromptInFlight. PIN authentication and the post-authentication wallet restoration interval are not protected.

When Android emits inactive/background during or immediately after authentication:

AppState
→ lockForBackground()
→ scheduleAutoLock(0)
→ lockWallet()
→ WalletAccessManager.onLock()
→ engine.discard()
→ currentWallet = null
→ status = locked

while FoundationScreen may already have:

view === 'wallet'

This produces:

authentication succeeds
→ wallet restoration
→ AppState auto-lock
→ currentWallet cleared
→ FoundationScreen sees wallet view + null wallet
→ "Preparing local vault"
→ eventually Locked.

IMPLEMENT THE FIX WITH THESE REQUIREMENTS:

1. Serialize the COMPLETE unlock transaction for BOTH PIN and biometric:

authentication start
→ authentication result
→ wallet restoration
→ currentWallet assignment
→ unlocked state stable.

2. AppState background/inactive locking must not interrupt the unlock transaction while it is actively authenticating/restoring the wallet.

3. Do NOT simply disable background locking.

4. If the application is still backgrounded when the unlock/restoration transaction completes, apply the pending background lock BEFORE exposing the wallet as unlocked.

5. Preserve the existing default auto-lock policy.

6. Preserve immediate in-memory secret clearing whenever a real lock is applied.

7. Preserve WalletAccessManager as the authoritative access/security boundary.

8. Fix the React/UI state synchronization so FoundationScreen receives an authoritative access-state update after unlock/restoration.

The UI must never remain in:

view === 'wallet'
AND
currentWallet === null

as a stable state.

Prefer a small subscription/state-version/event mechanism inside the existing WalletAccessManager boundary rather than introducing a new wallet state architecture.

IMPLEMENTATION GUIDANCE:

Use a single explicit unlock-in-progress state/guard owned by the security/access layer.

The guard must cover the entire operation, not just the biometric native prompt.

PIN and biometric must both use the same protection mechanism.

AppState handling should:

A. If no unlock transaction is active:
   preserve existing background-lock behavior.

B. If unlock transaction is active:
   record that a background/inactive event occurred and defer the lock.

C. After authentication + wallet restoration completes:
   - if the app is safely active, complete unlock normally;
   - if the app remains backgrounded/inactive according to the existing AppState policy, lock immediately before exposing the wallet.

Avoid creating multiple competing lock timers or duplicate lock callbacks.

Ensure the guard is cleared in all success, failure, cancellation, timeout, and exception paths.

UI STATE:

FoundationScreen should react to the authoritative access-state transition.

Do not solve this by polling getWallet().

Do not introduce arbitrary setTimeout delays.

Do not hide the Loading screen with a cosmetic change.

The actual access state must become consistent.
