==================================================
CRITICAL NON-CUSTODIAL SECURITY INVARIANT
==================================================

PrimeWave Wallet is strictly non-custodial.

Private keys and recovery phrases MUST:

- never leave the device
- never be sent to PrimeWave backend
- never be sent to RPC providers
- never be logged
- never be persisted outside the established secure vault
- never be exposed to React/UI components
- never be returned from public signing APIs
- never be included in transaction previews
- never be included in analytics
- never appear in errors
- never appear in telemetry
- never be copied to clipboard
- never be accessible to DApp code

Signing must happen entirely locally.

The only output of signing that may leave the signing boundary is the resulting signed transaction representation required by a future broadcasting layer.

PHASE 2.6 OBJECTIVE
==================================================

Implement a secure local signing engine.

The intended lifecycle is:

Unsigned Transaction
        ↓
Explicit Authorization
        ↓
Wallet Authentication
        ↓
Secure Key Access
        ↓
Local EVM Signing
        ↓
Signed Raw Transaction
        ↓
Sensitive Material Immediately Discarded
        ↓
Return Signed Transaction to controlled transaction layer
        ↓
STOP

Broadcasting is Phase 2.7.

==================================================
1. USE EXISTING SECURITY CONTRACTS
==================================================

Use the signing/security contracts established during Phase 0B.

Do NOT replace them with an unrelated architecture.

If existing contracts need extension:

- preserve backward compatibility
- keep the security boundary explicit
- document the reason for each change
- do not expose private keys through the new interfaces

The UI must never receive a private key.

The UI must never call a low-level private-key signing primitive directly.

==================================================
2. AUTHORIZATION IS REQUIRED
==================================================

Signing must require an explicit authorization object.

The signer must reject signing if authorization is absent or invalid.

Authorization should bind the signing request to the specific transaction.

At minimum, authorization must be associated with:

- wallet/account identity
- sender address
- network identity
- chain ID
- transaction identity / transaction digest
- authorization timestamp/context
- authentication state

The purpose is to prevent:

"Authenticate once → sign arbitrary transaction later."

The authorization must be specific to the transaction being signed.

==================================================
3. AUTHENTICATION
==================================================

Use the existing WalletAuthenticator architecture.

Signing must require the wallet to be authenticated/unlocked.

Authentication may be:

- PIN
- biometric authentication
- other existing approved local authentication mechanism

Do NOT create a second authentication system.

Do NOT store another PIN.

Do NOT bypass existing authentication.

Do NOT treat merely having an unlocked UI as authorization to sign arbitrary transactions.

==================================================
4. TRANSACTION BINDING
==================================================

Before signing, independently validate that the transaction being signed matches the authorization.

Verify:

- account ID
- FROM address
- network ID
- chain ID
- transaction type
- nonce
- gas limit
- value
- recipient
- calldata
- fee model
- fee fields

If any transaction-critical field differs:

REJECT SIGNING.

Do not silently rebuild.

Do not silently modify.

Do not "fix" the transaction.

Return a normalized security/signing error.

This is a critical anti-tampering boundary.

==================================================
5. SIGNING INPUT
==================================================

The signing engine should consume the validated unsigned transaction produced by Phase 2.5.

Do not allow arbitrary unvalidated transaction objects to reach the low-level signer.

If necessary, create a typed:

ValidatedUnsignedTransaction

or equivalent internal model.

The low-level signer should operate only on this validated representation.

==================================================
6. EVM SIGNING
==================================================

Use a well-maintained, standards-compliant EVM signing implementation.

Do NOT implement cryptographic primitives manually.

Use the existing approved dependency stack where possible.

The implementation must support:

- Legacy EVM transactions
- EIP-1559 transactions

The correct chain ID MUST be included.

Signing must follow standard Ethereum transaction serialization/signing rules.

Do not invent a custom PrimeWave transaction format.

PrimeWave Chain is EVM-compatible.

==================================================
7. PRIVATE KEY LIFETIME
==================================================

This is extremely important.

Private key material should exist in memory only for the minimum period required to derive/access the signing account and produce the signature.

Do NOT:

- put private keys in React state
- put private keys in Redux
- put private keys in context providers
- put private keys in global variables
- put private keys in caches
- put private keys in AsyncStorage
- put private keys in localStorage
- put private keys in logs
- put private keys in error objects
- put private keys in analytics
- put private keys in navigation parameters
- put private keys in URL parameters
- put private keys in test snapshots

Use the existing secure vault interface.

The signing layer must not persist extracted private key material.

==================================================
8. SECRET DISPOSAL
==================================================

After signing:

- release references to secret material
- do not retain the secret in service state
- do not cache it
- do not return it
- do not store it

Use best-effort memory cleanup where the language/runtime permits.

IMPORTANT:

Do NOT falsely claim that JavaScript/TypeScript can guarantee cryptographic memory zeroization.

Document the limitation clearly.

If a secure native implementation is required for stronger memory guarantees, document this as a future hardening item rather than pretending it is solved.

==================================================
9. NO SECRET EXPORT API
==================================================

Do NOT add public methods such as:

getPrivateKey()
exportPrivateKey()
getSeed()
getMnemonic()
getSecret()
retrieveRawKey()

The signer should not expose secret material to callers.

The secure vault remains the owner of sensitive wallet material.

==================================================
10. SIGNER INTERFACE
==================================================

Create a narrow signing interface.

Conceptually:

signTransaction(
  validatedUnsignedTransaction,
  authorization
)

returns something equivalent to:

SignedTransaction

containing only information needed by the future broadcast layer.

For example:

- rawTransaction
- transaction hash if deterministically available
- network ID
- chain ID
- transaction type

Do NOT return:

- private key
- mnemonic
- seed
- decrypted vault contents
- authentication credentials

The exact existing architecture should determine the final names.

==================================================
11. SIGNED RAW TRANSACTION
==================================================

The output must be a properly serialized signed EVM transaction.

It should be suitable for a future RPC broadcast call.

However:

DO NOT actually broadcast it.

Do NOT call:

eth_sendRawTransaction

The signed raw transaction must remain within the local transaction/security layer until Phase 2.7.

==================================================
12. TRANSACTION HASH
==================================================

If the chosen signing library provides deterministic transaction hashing:

calculate the transaction hash locally.

The hash is public information.

Do not query an RPC provider just to obtain the hash.

Do not broadcast to calculate the hash.

The hash must correspond exactly to the signed transaction.

If a hash cannot safely be produced with the current implementation, document it rather than inventing one.

==================================================
13. NETWORK PROTECTION
==================================================

Before signing:

verify:

- selected network
- network ID
- chain ID
- transaction chain ID
- authorization chain ID

All must match.

If the active network changes before signing completes:

REJECT.

Never sign a transaction against stale network context.

Do not automatically switch networks.

Do not automatically retry against another network.

==================================================
14. ACCOUNT PROTECTION
==================================================

Verify that:

- requested account exists locally
- authorization account matches transaction sender
- normalized sender address matches derived public account address

Never sign for a different account than the user authorized.

Do not automatically choose account 0.

Do not fall back to another account.

==================================================
15. SIGNING SHOULD BE EXPLICIT
==================================================

The signing API must NOT be triggered by:

- app startup
- background task
- app resume
- network refresh
- balance refresh
- token discovery
- DApp request
- timer
- notification
- automatic retry

Signing must require an explicit authorized call.

==================================================
16. PREVENT REPLAY / WRONG-CHAIN SIGNING
==================================================

The chain ID must be cryptographically bound into the transaction according to the transaction type.

Test that:

- signing on chain A produces a transaction bound to chain A
- the same unsigned transaction cannot be treated as authorized for chain B
- authorization for one chain cannot sign another chain's transaction

Do not implement custom replay protection.

Use standard EVM chain ID semantics.

==================================================
17. FEE INTEGRITY
==================================================

The signer must not modify:

- gas limit
- gas price
- max fee
- max priority fee
- nonce
- value

The signer is NOT a fee optimizer.

The signer consumes the already validated transaction.

If a field is invalid:

reject.

Do not silently correct it.

==================================================
18. VALUE / DATA INTEGRITY
==================================================

The signer must preserve exactly:

- recipient
- value
- calldata
- nonce
- gas
- fee parameters
- chain ID

Do not normalize in a way that changes transaction meaning.

Any canonical normalization must happen before the authorization binding or be included in the transaction digest.

==================================================
19. SECURITY ERRORS
==================================================

Use the existing sanitized error architecture.

Possible normalized errors:

- SIGNING_NOT_AUTHENTICATED
- SIGNING_NOT_AUTHORIZED
- SIGNING_TRANSACTION_MISMATCH
- SIGNING_ACCOUNT_MISMATCH
- SIGNING_NETWORK_MISMATCH

- SIGNING_VAULT_UNAVAILABLE
- SIGNING_KEY_ACCESS_FAILED
- SIGNING_FAILED
- SIGNING_CANCELLED

Do not expose:

- private key
- mnemonic
- seed
- decrypted vault contents
- raw cryptographic exceptions containing secrets
- secure storage values
- authentication secrets

==================================================
20. USER CANCELLATION
==================================================

Authentication can be cancelled.

If the user cancels:

- signing must stop
- no transaction should be signed
- no secret should be retained
- return a normalized cancellation error/state

Do not treat cancellation as a signing failure that might trigger automatic retry.

==================================================
21. BIOMETRIC BEHAVIOR
==================================================

Use the existing biometric architecture.

Do not create a separate biometric implementation.

If biometric authentication is unavailable:

allow the existing PIN fallback according to the established authentication policy.

If authentication times out:

return a normalized error.

Never leave the signer stuck in a "signing" state.

Physical Face ID testing is still deferred because Expo Go cannot provide the required native Face ID behavior.

Do not claim native biometric signing is physically verified yet.

==================================================
22. CONCURRENCY
==================================================

Protect against concurrent signing attempts.

Examples:

Request A starts signing.
Request B attempts to sign simultaneously.

Do not allow uncontrolled shared secret state.

Prefer one isolated signing operation at a time per wallet/account.

Reject or safely serialize concurrent signing attempts according to the existing architecture.

Do NOT queue arbitrary background signing requests.

==================================================
23. SIGNING SESSION LIFETIME
==================================================

Do not keep decrypted key material available after signing.

Authentication state may remain according to the existing wallet-locking policy, but key material must not.

Do not create a long-lived:

currentPrivateKey

signingKey

decryptedWallet

global secret cache

- PrimeWave backend
- analytics APIs
- cloud key services
- remote signing services

RPC is not required to sign.

A signing test must be able to run using a fake/offline environment.
