GENERIC ERC-20 TOKEN ENGINE

You are continuing development of PrimeWave Wallet.

DO NOT implement:

==================================================
NON-CUSTODIAL SECURITY INVARIANT
==================================================

PrimeWave Wallet is strictly non-custodial.

This phase is READ-ONLY.

The token engine MUST NEVER:

- access private keys
- access recovery phrases
- access seed material
- access SecureVault secrets
- unlock the wallet
- authenticate the user
- sign transactions
- broadcast transactions
- call eth_sendRawTransaction
- call token transfer()
- call approve()
- call transferFrom()
- call permit()
- persist secrets
- send secrets to any backend

Only public blockchain information may be used.

==================================================
PHASE 3.2 OBJECTIVE
==================================================

Build a generic ERC-20 token engine capable of representing arbitrary ERC-20 contracts on supported EVM networks.

The engine must support:

1. Token identity
2. Token contract validation
3. Token metadata retrieval
4. Token balance retrieval
5. Exact token amount handling
6. Network/account scoping
7. Non-standard metadata handling
8. Safe error handling
9. Read-only operation

The architecture must support future:

- user-added tokens
- discovered tokens
- verified tokens
- token visibility
- token transfers

without requiring a redesign.

But those features are NOT fully implemented in this phase.

==================================================
1. TOKEN IDENTITY
==================================================

Create a strongly typed ERC-20 token identity.

A token MUST NOT be identified only by:

- symbol
- name

The primary identity must include:

- asset type
- network ID
- contract address

Conceptually:

TokenAssetIdentity

{
  assetType: "fungible_token"
  networkId
  contractAddress
}

Normalize the contract address consistently.

Use checksum normalization where appropriate.

Two identical contract addresses on different networks MUST be treated as different assets.

Example:

USDC on Ethereum

and

USDC on Base

are distinct network-scoped token identities.

Do not merge them.

==================================================
2. TOKEN ASSET MODEL
==================================================

Create an ERC20Token model containing at minimum:

- asset type
- network ID
- chain ID
- contract address
- name
- symbol
- decimals
- metadata status
- verification status
- availability status

The architecture may include:

- verified
- user_added
- discovered
- unverified

but do not implement external verification/discovery services yet.

For Phase 3.2, default arbitrary contract tokens to an appropriate unverified/unknown verification state.

Do NOT call a token "verified" simply because it implements ERC-20 methods.

==================================================
3. TOKEN REGISTRY
==================================================

Extend the asset architecture with an ERC-20 token registry or equivalent.

Responsibilities:

- validate token identity
- normalize contract addresses
- resolve token by network + contract
- prevent duplicate token identities
- distinguish native assets from fungible tokens
- reject unsupported asset types

Do not create a hardcoded token list.

Do not hardcode:

- USDT
- USDC
- WBTC
- DAI
- LINK
- etc.

The engine must work with arbitrary ERC-20 contract addresses.

==================================================
4. NETWORK VALIDATION
==================================================

Every token operation MUST be network-scoped.

A token request must identify:

- network ID
- contract address

Before interacting with the contract:

- network must exist
- network must be enabled
- network must be configured
- network must be supported
- remote chain ID must match registry chain ID

Do not silently switch networks.

Do not use the currently selected network unless explicitly requested by the caller.

If using a convenience active-network method:

- resolve the active network
- reject if no active network exists
- never automatically switch

==================================================
5. CONTRACT ADDRESS VALIDATION
==================================================

Validate the ERC-20 contract address.

Requirements:

- valid EVM address
- canonical normalization
- reject malformed addresses

Do not accept arbitrary strings as contract addresses.

Do not treat a wallet EOA address as a token merely because it is syntactically valid.

==================================================
6. CONTRACT CODE VALIDATION
==================================================

Before treating an address as an ERC-20 contract:

use the existing public account-state / RPC infrastructure to determine whether code exists.

Use:

eth_getCode

If no contract code exists:

return a normalized:

TOKEN_NOT_A_CONTRACT

or equivalent error.

Do NOT assume:

"valid address = token contract"

This distinction is important.

Do not attempt to prove that arbitrary bytecode is a valid ERC-20 implementation solely from code existence.

==================================================
7. ERC-20 STANDARD INTERFACE
==================================================

Use the standard ERC-20 read methods:

balanceOf(address)
decimals()
symbol()
name()

These are READ-ONLY contract calls.

Use the existing RPC provider and:

eth_call

Do not create another RPC transport.

Do not make direct fetch requests.

Do not manually implement an RPC client.

==================================================
8. ABI IMPLEMENTATION
==================================================

Use a well-maintained existing ABI/encoding implementation.

The repository already uses viem.

Prefer existing viem primitives for:

- ABI encoding
- ABI decoding
- contract reads
- address handling

Do NOT manually implement:

- ABI encoding
- ABI decoding
- function selectors
- hexadecimal word encoding

unless the existing architecture genuinely requires it and there is no suitable existing primitive.

Do not add another Ethereum ABI library unnecessarily.

==================================================
9. TOKEN METADATA
==================================================

Implement read-only metadata retrieval.

Required metadata:

- name
- symbol
- decimals

Each should be retrieved safely.

Do not assume every contract behaves perfectly.

A contract may:

- revert
- return malformed data
- return unexpected values
- implement non-standard metadata behavior

Handle failures explicitly.

==================================================
10. METADATA FAILURE POLICY
==================================================

Do NOT fabricate token metadata.

Never substitute:

"Unknown Token"

as if it came from the blockchain without clearly representing it as a fallback display label.

Never invent:

- symbol
- decimals
- name

If metadata cannot be read:

return structured metadata status.

For example:

metadataStatus:
- complete
- partial
- unavailable
- invalid

Use safe display fallbacks only at the presentation layer.

The underlying token model must retain the fact that metadata is unavailable.

==================================================
11. SYMBOL HANDLING
==================================================

ERC-20 symbol responses may not always behave identically across contracts.

Support standard string responses.

Where practical, safely handle common legacy bytes32-style symbol responses.

Do NOT accept arbitrary malformed values.

Do not perform unsafe decoding.

If symbol decoding fails:

symbol = unavailable

rather than guessing.

==================================================
12. NAME HANDLING
==================================================

Name should be treated similarly.

If name() succeeds with a valid string:

use it.

If it reverts or returns invalid data:

mark name unavailable.

Do not fabricate a token name.

==================================================
13. DECIMALS HANDLING
==================================================

Decimals are extremely important.

The engine must validate:

- return value exists
- return value is an integer
- return value is within supported bounds

Use a conservative supported range.

Do not blindly trust arbitrary large decimals.

Phase 3.1 currently validates asset decimal metadata through a bounded range.

Use the established project policy consistently.

If decimals are invalid:

return normalized:

TOKEN_INVALID_DECIMALS

Do not silently replace invalid decimals with 18.

THIS IS CRITICAL.

Never assume ERC-20 decimals = 18.

==================================================
14. TOKEN BALANCE
==================================================

Implement:

getTokenBalance(networkId, tokenContract, account)

or equivalent.

The balance must be retrieved through:

balanceOf(account)

using eth_call.

The account must be:

- valid EVM address
- public address only

No private key.

No wallet unlock.

No authentication.

==================================================
15. ACCOUNT SCOPING
==================================================

Token balance identity must include:

- account ID
- account address
- network ID
- token contract address

Do not assume:

account 0.

Do not automatically choose the first account.

Do not merge balances from multiple accounts.

==================================================
16. EXACT TOKEN AMOUNTS
==================================================

Token raw balances MUST remain bigint.

Do not use:

Number()
parseFloat()
floating point
toFixed()

for financial calculations.

Example:

raw token balance:

123456789012345678901234567890n

must remain exact.

Use the existing Phase 3.1 amount formatting infrastructure where appropriate.

==================================================
17. TOKEN AMOUNT FORMATTING
==================================================

Token display formatting must use:

token.decimals

not:

native asset decimals.

Example:

USDC-like token:
6 decimals

Some other token:
18 decimals

Both must display according to their own contract metadata.

Do not hardcode decimals based on token symbol.

==================================================
18. TOKEN AMOUNT PARSING
==================================================

Reuse Phase 3.1 exact decimal parsing.

For future token transaction UI:

parse:

"1.5"

using:

token.decimals

to obtain exact bigint base units.

Do NOT connect this to token transfers yet.

==================================================
19. TOKEN BALANCE RESULT
==================================================

Create a structured result similar to:

TokenBalance

containing:

- asset identity
- token contract
- network ID
- chain ID
- account ID
- account address
- raw balance bigint
- decimals
- formatted balance
- symbol if available
- token name if available
- retrieval timestamp
- block context where available
- metadata status

No secrets.

23. CONTRACT CALL SAFETY
==================================================

All token metadata/balance calls are read-only.

The engine may use:

eth_call

- to = token contract
- data = encoded read method
- block context where supported

Do NOT send:

- value
- gas for state-changing calls
- signing data

Do not call state-changing token methods.

==================================================

==================================================

The Phase 3.2 engine MUST NOT invoke:

Also do not implement:

==================================================
25. TOKEN VERIFICATION
==================================================

Do not claim a token is legitimate merely because:

- contract code exists
- name exists
- symbol exists
- decimals exists
- balanceOf works

ERC-20 compatibility is not the same thing as asset legitimacy.

Create an explicit verification status model.

Possible values:

unknown
unverified
verified

For Phase 3.2, arbitrary contracts should remain:

unknown/unverified

unless a trusted verification source already exists.

Do not integrate a third-party verification provider yet.

- scam

- spam

- eth_getCode

- eth_call for decimals

- eth_call balanceOf

Do not repeatedly retrieve metadata when the same in-memory operation already has it.

However:

DO NOT create a persistent token cache in Phase 3.2.

Future caching can be designed deliberately.

==================================================
32. CONCURRENCY
==================================================

Protect against uncontrolled duplicate reads where practical.

Examples:

Two identical metadata requests occur simultaneously.

Avoid unnecessary duplicate work within a single service operation where reasonable.

Do not introduce global mutable token state.

Do not persist token state.

==================================================
33. NETWORK RACE PROTECTION
==================================================

Capture network context before token operations.

Verify:

- network ID
- chain ID
- configured network

before returning results.

If an active-network convenience method is being used and the active network changes:

reject with:

NETWORK_CHANGED

Do not silently return data from a different network.

Explicitly network-scoped requests should remain tied to their requested network.

==================================================
35. SAFE METADATA LIMITS
==================================================

Treat token-returned strings as untrusted external data.

Do not allow arbitrary contract metadata to:

- execute code
- become HTML
- become a navigation URL
- become a file path
- become an image URL automatically
- become an analytics identifier without sanitization

Metadata is display data.

Apply reasonable length limits to:

- token name
- token symbol

Do not allow enormous RPC return values to create memory abuse.

Document chosen limits.

Do not silently truncate the canonical metadata value if doing so would change identity; use a display-only truncation layer where appropriate.
