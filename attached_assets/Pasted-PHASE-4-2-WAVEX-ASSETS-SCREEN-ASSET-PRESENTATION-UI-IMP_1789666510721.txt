PHASE 4.2 — WAVEX ASSETS SCREEN & ASSET PRESENTATION UI

IMPORTANT:
This is a controlled UI implementation phase.

PRODUCT NAME:
WAVEX

Do NOT display “PrimeWave Wallet” as the product name.
Do NOT display “by PrimeWave” in the WaveX product branding.

PrimeWave remains the ecosystem/network name where applicable.

==================================================

==================================================

The attached image is the PRIMARY VISUAL DESIGN REFERENCE for this phase.

Use the attached WaveX Wallet UI reference image to guide:

- visual hierarchy
- screen composition
- spacing
- typography hierarchy
- card treatment
- rounded surfaces
- dark background
- cyan / electric blue / violet accents
- subtle glow effects
- icon treatment
- asset rows
- navigation styling
- buttons
- borders
- gradients
- overall premium futuristic Web3 aesthetic

The reference image represents the intended WaveX design language.

IMPORTANT:

Do NOT blindly copy example balances, token names, addresses, text, or functionality shown in the image.

Use the existing real application data and architecture.

The image is a VISUAL DESIGN REFERENCE, not a functional specification.

Existing application architecture and security rules take priority over the visual reference.

Do not introduce functionality merely because it appears in the image.

==================================================
OBJECTIVE
==================================================

Build the real WAVEX Assets screen.

The Assets screen must consume the existing:

PortfolioReadModelService
        ↓
PortfolioAssetViewModel
        ↓
Assets UI

Do NOT duplicate blockchain logic.

Do NOT implement a second asset engine.

Do NOT make direct RPC calls from UI components.

==================================================
1. ASSETS SCREEN
==================================================

Create the production-style Assets screen shown conceptually in the attached reference.

The screen should include:

HEADER

- back/home navigation where appropriate
- WAVEX branding
- appropriate account/network context
- clean futuristic styling

TITLE

“Assets”

Provide a concise portfolio/asset summary.

Do not introduce fiat valuation.

==================================================
2. SEARCH
==================================================

Add an asset search field.

Search should operate on the existing read-model asset collection.

Allow searching by appropriate public presentation fields such as:

- asset name
- symbol
- contract address where applicable

Search must be:

- case-insensitive
- deterministic
- local/in-memory
- UI-only filtering

Do NOT make network requests for search.

Do NOT call external token-list services.

Do NOT call price APIs.

==================================================
3. ASSET FILTERS
==================================================

Add a clean filter/segmentation treatment consistent with the reference.

At minimum support:

- All
- Visible
- Hidden

Use the existing visibility state.

Do NOT redefine visibility semantics.

Do NOT treat:

hidden
as
unverified
or
unavailable.

These are separate concepts.

If verification filtering is later added, it must remain independent.

==================================================
4. ASSET LIST
==================================================

Render assets from PortfolioReadModel.

Each asset row should be visually polished and may include:

- token/native icon
- asset name
- symbol
- formatted balance
- availability state
- verification indicator where appropriate
- metadata state where appropriate
- navigation affordance for future asset details

Use existing AssetIcon / TokenLogo abstraction.

Do NOT invent token logos.

Do NOT infer trust from logos.

Do NOT infer verification from logos.

==================================================
5. NATIVE ASSET
==================================================

Native assets should have a visually distinct but consistent presentation.

Use the existing network/native currency metadata.

Do NOT hardcode:

- ETH
- BNB
- MATIC
- PrimeWave currency

when the active network model already provides the information.

The UI should consume the existing network/asset models.

==================================================
6. ERC-20 ASSETS
==================================================

ERC-20 assets must use the existing PortfolioAssetViewModel.

Display:

- name
- symbol
- formatted balance
- icon/fallback
- verification status where appropriate

Preserve exact balance formatting.

Do not perform floating-point conversion of raw token balances.

Do not calculate fiat values.

==================================================
7. ASSET STATES
==================================================

Clearly represent the existing states.

Balance:

- positive
- zero
- unavailable

Availability:

- available
- unavailable
- stale
- invalid

Metadata:

- complete
- partial
- unavailable
- invalid

Verification:

- verified
- unverified
- unknown

Visibility:

- visible
- hidden

Do NOT collapse these concepts into one generic status.

For example:

An unverified token can still have an available balance.

A token with zero balance is not necessarily unavailable.

A hidden token is not necessarily unverified.

==================================================
8. VERIFICATION PRESENTATION
==================================================

If the read model reports:

verified

the UI may show a clear verification indicator.

If:

unverified
or
unknown

do not present the asset as verified.

Do NOT use:

- token logo
- token name
- symbol
- discovery
- transfer history
- popularity
- balance

as verification evidence.

Do not label a token “scam” or “malicious”.

==================================================
9. ICON / LOGO BEHAVIOR
==================================================

Use the existing AssetIcon / TokenLogo architecture.

The visual hierarchy should support:

1. trusted logo if a future trusted source exists
2. deterministic asset fallback
3. native asset fallback
4. initials/placeholder fallback

Do NOT add an external logo API.

Do NOT add token-list providers.

Do NOT use logo presence as a trust signal.

The implementation should make future logo providers possible without changing the Assets UI contract.

==================================================
10. EMPTY STATE
==================================================

If there are no visible assets:

Show a polished empty state.

Explain that assets will appear when available.

Do not invent balances.

Do not show fake demo tokens in production/native mode.

Preview Test Mode may continue using its existing fixed public development display model where already supported.

==================================================
11. UNAVAILABLE STATE
==================================================

If blockchain data is unavailable:

Show an honest unavailable state.

Do NOT display:

0.00

as a substitute for unavailable blockchain data.

Do not imply the wallet has zero assets when the actual state is unavailable.

==================================================
12. LOADING STATE
==================================================

Create a polished loading/skeleton state consistent with the attached reference.

Do not use an excessive spinner-only experience.

The loading state should visually resemble the final Assets screen structure.

==================================================
13. ERROR STATE
==================================================

Use sanitized application errors.

Do not display:

- raw RPC errors
- stack traces
- internal file paths
- RPC credentials
- private URLs

Provide a clear retry/refresh affordance where appropriate.

==================================================
14. REFRESH
==================================================

Provide an explicit refresh action.

Use the existing read-model/portfolio runtime.

Do NOT introduce:

- background polling
- new caching
- persistence
- automatic retry loops

Do not duplicate blockchain requests.

==================================================
15. ASSET DETAIL ENTRY POINT
==================================================

Asset rows may be tappable/clickable to prepare for a future Asset Detail screen.

However:

DO NOT build the full Asset Detail screen in this phase.

If necessary, use a controlled placeholder such as:

“Asset details coming soon.”

Do not create fake transaction or price information.

==================================================
16. NAVIGATION
==================================================

Integrate Assets into the existing bottom navigation.

Existing destinations:

- Home
- Assets
- Swap
- Activity
- Settings

Assets becomes the second fully implemented destination.

Home remains functional.

Other destinations remain controlled placeholders.

Do not redesign their functionality in this phase.

==================================================
17. HOME → ASSETS
==================================================

The Home screen's:

“View All”

or equivalent asset navigation should open the real Assets screen.

The Assets screen must use the same underlying portfolio/read-model architecture.

Do not create separate asset data for Home and Assets.

Both should consume the same source of truth.

==================================================
18. NETWORK CONTEXT
==================================================

Assets are always scoped to:

account + network.

Do not merge assets from multiple networks.

Do not silently switch networks.

If the active network is:

unconfigured
or
unavailable

display the appropriate existing state.

Do not invent PrimeWave Mainnet configuration.

==================================================
19. ACCOUNT CONTEXT
==================================================

Assets must remain scoped to the authenticated/public account context.

Do not display another account's assets.

Do not implement account switching in this phase.

Do not implement account import or creation.
