==================================================
1. OBJECTIVE
==================================================

Build a UI-independent transaction broadcasting and confirmation engine.

Responsibilities:

1. Validate the signed transaction is appropriate for the currently selected network.
2. Broadcast it through the existing EVM RPC provider.
3. Receive the transaction hash.
4. Monitor blockchain state for the transaction.
5. Detect successful confirmation.
6. Detect reverted transaction.
7. Detect dropped/not-found transaction according to a clearly defined policy.
8. Prevent accidental duplicate broadcast attempts.
9. Prevent network mismatch.
10. Normalize errors.
11. Never sign.
12. Never access secrets.

==================================================
2. REUSE EXISTING RPC PROVIDER
==================================================

Use the existing EvmRpcProvider.

Do not create a second RPC implementation.

The existing provider already supports:

eth_sendRawTransaction

Use that existing method.

Do not bypass the provider with direct fetch calls.

Do not create another HTTP client.

==================================================
3. BROADCAST INPUT
==================================================

The broadcaster must accept a narrow signed transaction model from Phase 2.6.

Conceptually:

SignedTransaction

containing:

- rawTransaction
- transactionHash if available
- networkId
- chainId
- transactionType

The exact project types should be reused.

Do not accept:

- private key
- mnemonic
- seed
- wallet password
- PIN
- decrypted vault
- arbitrary unsigned transaction

The broadcaster must NOT be capable of signing.

==================================================
4. VALIDATE SIGNED TRANSACTION
==================================================

Before broadcasting validate:

- raw transaction exists
- raw transaction is valid 0x-prefixed hex
- raw transaction contains valid byte data
- network ID is valid
- network is enabled
- network is configured
- network is currently active
- chain ID matches the active network
- signed transaction chain context matches expected chain
- transaction hash, if supplied, is internally consistent where practical

If the active network differs:

REJECT.

Do not switch networks automatically.

Do not broadcast.

==================================================
5. CHAIN ID PROTECTION
==================================================

Before broadcasting:

1. Obtain the active network.
2. Verify its configured chain ID.
3. Verify remote RPC chain ID.
4. Verify signed transaction chain ID.
5. Verify all three match.

If any mismatch occurs:

STOP.

Return a normalized chain/network mismatch error.

Never broadcast a transaction to a chain different from the one it was signed for.

==================================================
6. DO NOT MODIFY SIGNED TRANSACTION
==================================================

Once signed:

DO NOT modify:

- nonce
- gas limit
- gas price
- max fee
- max priority fee
- recipient
- value
- calldata
- chain ID
- transaction type

The broadcaster must transmit the signed raw transaction exactly as received.

No:

- gas changes
- fee changes
- nonce changes
- formatting changes that alter bytes
- transaction rebuilding
- re-signing

The raw signed bytes are immutable for the broadcast operation.

==================================================
7. FIRST BROADCAST
==================================================

Broadcast using:

eth_sendRawTransaction

The RPC response should contain a transaction hash.

Validate the response.

Do not blindly trust malformed RPC responses.

If the RPC response is malformed:

return a normalized error.

==================================================
8. TRANSACTION HASH
==================================================

Where practical:

calculate or verify the transaction hash locally using the same standard transaction hashing rules used during Phase 2.6.

Compare it with the RPC returned hash.

If they do not match:

DO NOT report success.

Return a normalized transaction-hash-mismatch error.

Do not automatically rebroadcast.

If the existing signing layer already provides a trusted hash, reuse it.

Do not duplicate cryptographic implementations unnecessarily.

==================================================
9. DUPLICATE BROADCAST PROTECTION
==================================================

This is critical.

A broadcast operation must not accidentally submit the same signed transaction repeatedly because of:

- UI double tap
- network timeout
- React rerender
- retry
- duplicate callback
- app lifecycle event
- concurrent calls

Because the same signed transaction can be submitted more than once by accident, the engine must maintain an in-memory broadcast operation guard.

Use a deterministic transaction identity such as:

transaction hash

or a safe hash of the signed bytes.

If the same transaction is already being broadcast:

- do not start another independent broadcast operation
- return/reuse the existing operation state according to the architecture

Do not create persistent transaction queues yet.

Do not implement transaction replacement.

==================================================
10. TIMEOUT SEMANTICS
==================================================

This is extremely important.

An RPC timeout does NOT necessarily mean the transaction was not accepted.

Example:

Wallet → RPC
RPC accepts transaction
RPC → Wallet response is lost
Wallet sees timeout

The transaction may already be in the mempool.

Therefore:

DO NOT automatically rebroadcast after a timeout.

Return a state such as:

BROADCAST_STATUS_UNKNOWN

and allow the transaction hash to be determined/reconciled through an appropriate later lookup mechanism if possible.

Never claim:

"Transaction failed"

solely because the HTTP/RPC request timed out.

==================================================
11. ERROR CLASSIFICATION
==================================================

Normalize broadcast errors into clear categories.

At minimum consider:

- BROADCAST_NETWORK_UNAVAILABLE
- BROADCAST_TIMEOUT
- BROADCAST_RPC_ERROR
- BROADCAST_REJECTED
- BROADCAST_MALFORMED_RESPONSE
- BROADCAST_CHAIN_MISMATCH
- BROADCAST_NETWORK_CHANGED
- BROADCAST_INVALID_TRANSACTION
- BROADCAST_HASH_MISMATCH
- BROADCAST_ALREADY_IN_PROGRESS
- BROADCAST_UNKNOWN_RESULT

Do not expose raw RPC payloads containing sensitive information.

Do not include:

- private keys
- mnemonic
- vault contents
- authentication secrets
- full internal stack traces

==================================================
12. RPC ERROR INTERPRETATION
==================================================

Common EVM rejection cases may include:

- insufficient funds
- nonce too low
- nonce too high
- replacement transaction underpriced
- intrinsic gas errors
- invalid sender
- execution-related rejection
- already known

Do not automatically retry rejected transactions.

Do not automatically modify the transaction.

Do not increase fees.

Do not change nonce.

Normalize the error while preserving useful information for a future UI.

"already known" must NOT automatically be treated as a new successful transaction unless the transaction hash can be safely established.

==================================================
13. RECEIPT MONITORING
==================================================

After a successful broadcast response:

monitor:

eth_getTransactionReceipt

for the transaction hash.

Use the existing RPC provider.

Do not create a second RPC client.

==================================================
14. CONFIRMATION STATES
==================================================

Create a clear transaction lifecycle.

At minimum:

CREATED / READY
BROADCASTING
BROADCASTED
CONFIRMING
CONFIRMED
REVERTED
FAILED
UNKNOWN

Use appropriate naming consistent with the existing architecture.

Important distinction:

BROADCASTED
does not mean
CONFIRMED.

A transaction is only confirmed when an appropriate receipt is observed.

==================================================
15. RECEIPT HANDLING
==================================================

For a valid receipt:

Read:

- transactionHash
- blockHash
- blockNumber
- status
- gasUsed
- effectiveGasPrice where available

Do not assume all networks provide identical optional fields.

Use bigint for numeric blockchain quantities.

Receipt status should be interpreted according to standard EVM semantics.

If status indicates success:

CONFIRMED

If status indicates failure/revert:

REVERTED

Do not call a reverted transaction "successful."

==================================================
16. CONFIRMATION COUNT
==================================================

For initial Phase 2.7:

A receipt in a block may be treated as the first confirmation.

Do not build a sophisticated multi-confirmation policy yet unless the existing architecture already requires it.

However, design the model so future phases can support:

- required confirmations
- current confirmations
- finalized state

Do not pretend "receipt exists" means irreversible finality on every chain.

==================================================
17. POLLING
==================================================

Implement controlled receipt polling.

Requirements:

- bounded polling
- configurable interval
- configurable timeout
- no infinite loop
- no aggressive polling
- no polling when transaction is already terminal

Suggested defaults can be selected sensibly, but document them.

Do not poll every second forever.

Do not run receipt polling globally in the background.

The polling engine should be explicitly invoked.

==================================================
18. APP LIFECYCLE
==================================================

Do not allow app lifecycle events to trigger automatic broadcasting.

App resume may later support explicit transaction-status reconciliation, but do not automatically broadcast.

If polling is interrupted because the app is backgrounded:

- do not rebroadcast
- do not assume failure
- preserve enough non-secret transaction identity to allow later reconciliation

Do not persist anything in this phase unless absolutely necessary for the explicitly implemented lifecycle behavior.

==================================================
19. DROPPED / NOT FOUND TRANSACTIONS
==================================================

Do NOT immediately label a transaction as dropped because:

eth_getTransactionReceipt

returns null.

A pending transaction naturally has no receipt.

Also do not declare it permanently dropped based solely on a short timeout.

For this phase:

- null receipt during polling = still pending/unknown
- polling timeout = confirmation unknown/pending
- do not rebroadcast automatically

If implementing transaction lookup via:

eth_getTransactionByHash

use it only for reconciliation and status observation.

Do not treat absence from one RPC endpoint as proof that the transaction never existed.

Document provider/mempool visibility limitations.

==================================================
20. TRANSACTION HASH LOOKUP
==================================================

If practical, support read-only lookup using:

eth_getTransactionByHash

This can help reconcile:

- RPC timeout
- app restart
- delayed receipt

However:

Do not build a full transaction indexing system.

Do not persist a transaction database.

Do not create transaction history.

This is only broadcast/confirmation infrastructure.

==================================================
21. ENDPOINT FAILOVER
==================================================

DO NOT implement automatic multi-RPC failover in this phase.

The existing provider may have endpoint priority.

Do not add sophisticated failover behavior.

Why:

A broadcast timeout can be ambiguous.

Sending the same transaction to another endpoint may be safe from a protocol perspective because the transaction hash is deterministic, but the application must not hide ambiguity behind aggressive retries.

Keep behavior deterministic.

Endpoint health/failover remains a separate future concern.

==================================================
22. NETWORK RACE PROTECTION
==================================================

Capture network context before broadcast:

- network ID
- chain ID
- active network identity

Verify it again before sending.

If the network changes:

STOP.

Do not broadcast.

After broadcast, confirmation lookup must remain tied to the transaction's original network.

Do not accidentally query the new active network for the old transaction.

This is especially important if the user switches networks while a transaction is confirming.

==================================================
23. ORIGINAL NETWORK CONTEXT
==================================================

The confirmation engine must not depend solely on the CURRENT active network.

A transaction belongs to the network on which it was signed and broadcast.

Therefore confirmation requests should use the transaction's original network context.

However:

Do not automatically switch the user's active network.

The confirmation engine may use the appropriate configured RPC provider for the transaction's network without changing UI network selection.
