==================================================
1. OBJECTIVE
==================================================

Build the WAVEX Activity page using the attached Activity screenshot as the PRIMARY UX / INFORMATION-ARCHITECTURE REFERENCE.

The desired experience is:

A wallet-native, asset-first transaction feed.

The asset/token logo is the primary visual anchor.

A small network icon/badge overlaps the bottom-right corner of the asset logo.

The action appears beside the asset:

- Sent USDT
- Received USDT
- Swapped
- Contract Interaction
- etc.

The counterparty/action context appears underneath.

The amount is right-aligned.

Optional fiat value appears underneath the amount.

Activities are grouped by date.

4. HEADER
==================================================

Header:

- back/navigation behavior consistent with the existing app
- title: "Activity"

If Activity is accessed through bottom navigation, maintain the normal WAVEX navigation experience.

==================================================
5. FILTER CONTROLS
==================================================

At the top, create two compact controls inspired by the reference:

1. Activity type filter

Default:

"Transactions"

Possible future values may include:

- Transactions
- Swaps
- Approvals
- Contract Interactions
- All Activity

Do NOT implement filtering for unsupported future event types unless corresponding activity records exist.

2. Network filter

Default:

"All networks"

Allow selecting among registered/enabled networks.

Do not silently change the wallet's active network merely because the Activity filter changes.

IMPORTANT:

Activity network filtering is a DISPLAY FILTER.

It must NOT modify the active wallet network.

Account/network security context remains separate from display filtering.

==================================================
6. ACTIVITY DATA SOURCE
==================================================

Activity UI MUST consume:

ActivityReadModelService

and the existing ActivityPresentationModel.

Do NOT:

- directly call RPC from UI
- directly call blockchain APIs
- query transaction receipts from UI
- reconstruct transactions in UI
- calculate blockchain amounts in UI
- create a second activity repository

The UI is a presentation layer.

==================================================
7. ASSET-FIRST ACTIVITY ROW
==================================================

Create a reusable ActivityRow component.

Conceptual structure:

LEFT:

Large primary asset/token icon.

BOTTOM-RIGHT OVERLAY:

Small network badge/icon.

CENTER:

First line:
Action + asset

Examples:

"Sent USDT"
"Received USDT"
"Sent BNB"
"Contract Interaction"

Second line:

Counterparty or event context.

Examples:

"To: 0x3bf79...35C96"
"From: 0x42A1...7B92"
"Contract: 0x0083...985h"

RIGHT:

Primary amount.

Examples:

"-10 USDT"
"+25 USDT"
"-0.01062 BNB"

Second line:

Optional fiat value.

Example:

"-$10.00"

If fiat is unavailable:

Do not invent a value.

The UI may simply omit the fiat line.

==================================================
8. TOKEN ICON
==================================================

Reuse existing:

AssetIcon / TokenLogo architecture.

Do NOT create a new icon system.

For missing/unavailable token logos:

use the existing deterministic fallback.

The icon must never be treated as proof of token legitimacy.

==================================================
9. NETWORK BADGE
==================================================

Overlay the network badge on the bottom-right of the asset icon.

The visual relationship should closely resemble the attached reference.

The badge should:

- be clearly recognizable
- remain small relative to the asset icon
- not obscure the primary asset logo
- have an appropriate border/background for separation
- use existing network metadata

Reuse NetworkRegistry.

Do not add an external logo provider.

If a network has no actual icon asset:

use the presentation model's deterministic fallback.

Never fabricate a real logo.

==================================================
10. SENT ACTIVITY
==================================================

For outgoing transactions:

Display:

"Sent {ASSET}"

and:

"To: {shortened address}"

Amount:

"-{amount} {symbol}"

Do not infer fiat value without legitimate price data.

==================================================
11. RECEIVED ACTIVITY
==================================================

For incoming transactions:

Display:

"Received {ASSET}"

and:

"From: {shortened address}"

Amount:

"+{amount} {symbol}"

Use the existing direction model.

Do not infer received status from UI assumptions.

==================================================
12. SELF TRANSFER
==================================================

For self-transfer:

Do not incorrectly label it simply as Sent or Received if the presentation model identifies:

self_transfer

Use a clear label such as:

"Self transfer"

or another neutral presentation.

Preserve the underlying direction.

==================================================
13. CONTRACT INTERACTION
==================================================

For generic contract interactions:

Display:

"Contract Interaction"

or an appropriately specific action only when authoritative data supports it.

Show:

"Contract: 0x..."

Do not pretend an unknown contract interaction was a token transfer.

Do not infer Swap.

Do not infer Approval unless authoritative activity data identifies it.

==================================================
14. SWAP UI PREPARATION
==================================================

The UI should be capable of rendering future explicit swap presentation records.

For example:

"Swapped"

"BNB → USDT"

Right side:

"+1.0655 USDT"
"-0.0015 BNB"

The exact visual arrangement can use a compact two-line representation.

IMPORTANT:

Do not create swap detection.

Do not infer swaps from arbitrary transactions.

Only render:

action = swapped

when the ActivityPresentationModel explicitly provides a trusted multi-asset swap representation.

Swap execution remains a future phase.

==================================================
15. STATUS INDICATORS
==================================================

Support existing lifecycle states.

At minimum visually distinguish:

- broadcasting
- broadcasted
- confirming
- confirmed
- reverted
- failed
- unknown

Pending states may use subtle status indicators.

Confirmed transactions should look settled.

Reverted/failed transactions must be visually distinguishable without using sensational design.

Unknown must not be shown as failed.

Do not show:

"Success"

unless the underlying state is actually confirmed.

Do not show:

"Sent"

as proof of on-chain confirmation.

==================================================
16. DATE GROUPING
==================================================

Group activity chronologically.

Examples:

Today

Yesterday

Sep 16, 2026

Sep 11, 2026

Sep 10, 2026

Use the presentation model's timestamp and timestamp source.

Do not claim a blockchain date if only observation time exists.

Newest activity first.

Use deterministic ordering from the ActivityReadModelService.

==================================================
17. EMPTY STATES
==================================================

Implement polished states for:

- no activity
- no activity on selected network
- no matching activity filter
- unavailable activity data
- loading
- refresh error

Example:

"No transactions yet"

with a concise WAVEX visual treatment.

Do not create fake activity to make the screen look populated.

==================================================
18. REFRESH
==================================================

Provide a user-triggered refresh action.

Use the existing Activity architecture.

Do NOT add:

- infinite polling
- aggressive background polling
- automatic rebroadcast
- direct receipt polling from UI

Activity UI refresh must remain separate from transaction execution.

==================================================
19. ACCOUNT ISOLATION
==================================================

The Activity page must always reflect the currently active account.

If the account changes:

- activity read model must update
- previous account's activity must disappear
- no cross-account records may remain visible

Do not rely solely on UI filtering.

The service/repository architecture remains authoritative.

==================================================
20. NETWORK FILTER VS ACTIVE NETWORK
==================================================

IMPORTANT DISTINCTION:

The Activity network filter is NOT the same as the wallet's active network selector.

For example:

Wallet active network:
Ethereum

Activity filter:
All networks

must be allowed.

Activity filter:
Base

must show Base activity without changing the wallet's active network.

Do not call:

NetworkRegistry.selectActiveNetwork()

when the user changes the Activity display filter.

==================================================
21. TRANSACTION SELECTION
==================================================

Each activity row should be tappable.

For now:

tap → controlled transaction detail placeholder

Do NOT build the complete transaction detail page in this phase.

Pass only the activity identifier / safe public context.

Do not pass:

- private key
- mnemonic
- signing capability
- PIN
- authentication secrets

==================================================
22. EXPLORER
==================================================

Where the Activity presentation model provides a valid configured explorer transaction URL:

allow the future detail flow to use it.

Do not open arbitrary URLs from activity data.

Do not invent explorer URLs.

Do not display explorer actions for placeholder/unconfigured networks.

If useful, the Activity row/detail placeholder may indicate explorer availability.

==================================================
23. FIAT VALUE
==================================================

The Activity UI must support optional fiat values.

If:

fiatValue != null

display it.

If:

fiatValue == null

omit it cleanly.

Do NOT:

- hardcode $1 = 1 USDT
- calculate fiat from token symbol
- use fake sample prices
- call external price APIs

Price infrastructure will be introduced later.

==================================================
24. PERFORMANCE
==================================================

Use bounded ActivityReadModel results.

Do not render unbounded transaction history.

Use efficient list rendering appropriate for React Native.

Avoid unnecessary rerenders.

Do not perform blockchain calls for every ActivityRow.

==================================================
25. ACCESSIBILITY
==================================================

Activity rows must have:

- accessible labels
- readable amounts
- readable status
- accessible action descriptions
- sufficient contrast
- appropriate touch target
- meaningful labels for network badge where needed

A screen reader should be able to understand something equivalent to:

"Sent 10 USDT to 0x3bf79...35C96 on Ethereum"

without requiring visual interpretation.
