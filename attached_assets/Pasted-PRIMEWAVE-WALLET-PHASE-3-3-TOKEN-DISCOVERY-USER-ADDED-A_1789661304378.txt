==================================================
CORE PRINCIPLE
==================================================

Discovery, identity, compatibility, metadata, verification, and trust are different concepts.

DO NOT collapse them.

A token can be:

DISCOVERED
without being
VERIFIED.

A token can be:

ERC-20 COMPATIBLE
without being
TRUSTED.

A token can have:

VALID METADATA
without being
LEGITIMATE.

A token can have the same:

NAME / SYMBOL

as another token while having a completely different contract address.

The contract address + network remains the authoritative asset identity.

==================================================
PHASE 3.3 OBJECTIVE
==================================================

Create a safe discovery and user-added token architecture.

The system should support:

1. Known token candidates
2. User-added tokens
3. Discovered token candidates
4. Token visibility state
5. Deduplication
6. Network/account scoping
7. Safe metadata resolution
8. Discovery provenance
9. Explicit verification state
10. Future trusted-token integration

But DO NOT build a full external token verification provider.

==================================================
1. TOKEN SOURCE / PROVENANCE
==================================================

Create a strongly typed token provenance model.

Possible values:

- user_added
- discovered
- registry
- external_source

Only sources appropriate to this phase should be functional.

At minimum implement:

user_added
discovered

The architecture may reserve:

registry
external_source

for future use.

Every token candidate should carry provenance.

This allows future UI to explain:

"Added by you"

versus:

"Discovered on-chain"

without implying trust.

==================================================
2. TOKEN DISCOVERY STATUS
==================================================

Create a discovery state model.

Possible states:

- not_discovered
- discovered
- manually_added
- hidden
- unavailable

Use terminology consistent with the existing project.

Do not automatically use:

verified

as a discovery state.

Verification is a separate concern.

==================================================
3. TOKEN VERIFICATION STATUS
==================================================

Reuse/extend the Phase 3.2 verification model.

At minimum:

- unknown
- unverified
- verified

For Phase 3.3:

DO NOT implement a real verification provider.

DO NOT automatically set arbitrary discovered tokens to verified.

DO NOT infer verification from:

- contract code
- name
- symbol
- decimals
- balance
- transfer history
- token popularity

All arbitrary discovered/user-added tokens should remain:

unknown/unverified

unless a trusted source already exists in the project.

==================================================
4. USER-ADDED TOKEN
==================================================

Create a user-added token request/model.

The minimum required input should be:

- network ID
- contract address

The system should then:

1. Validate network
2. Validate address
3. Validate contract code
4. Read ERC-20 metadata
5. Resolve token identity
6. Create a token candidate
7. Mark provenance as user_added
8. Mark verification as unknown/unverified
9. Return the token result

Do NOT automatically claim the token is legitimate.

==================================================
5. USER-ADDED TOKEN PERSISTENCE
==================================================

This phase MAY introduce persistence for user-added token preferences.

However:

ONLY non-sensitive public metadata may be persisted.

Allowed examples:

- network ID
- contract address
- asset identity
- visibility
- provenance
- locally observed metadata
- timestamps

Forbidden:

- private keys
- mnemonic
- seed
- PIN
- vault contents
- authentication secrets
- signing data

Do NOT use SecureStore for token metadata.

If persistence is implemented, use an appropriate non-sensitive local storage abstraction already accepted by the project.

If the project does not yet have an approved persistence abstraction:

create a small isolated public-metadata persistence interface.

Do not directly scatter AsyncStorage/localStorage calls throughout the token engine.

==================================================
6. WEB / BROWSER STORAGE
==================================================

Follow the existing project security policy.

Do NOT introduce insecure fallback behavior merely to make persistence work on web.

If secure/public persistence is unsupported in a specific environment:

fail safely or operate session-only according to the established architecture.

Do not persist token metadata in inappropriate secret storage.

==================================================
7. TOKEN IDENTITY
==================================================

The canonical token identity remains:

assetType
+
networkId
+
contractAddress

Do NOT use:

symbol
name
decimals

as identity.

Normalize contract addresses consistently.

Example:

Ethereum + 0xABC...

is different from:

Base + 0xABC...

==================================================
8. DEDUPLICATION
==================================================

Prevent duplicate token records.

These must resolve to the same identity:

Ethereum + contract A

Ethereum + same contract A

regardless of:

- checksum casing
- provenance
- repeated discovery

However:

Ethereum + contract A

must remain distinct from:

Base + contract A

If a token is:

user_added

and later:

discovered

do NOT create two token identities.

Instead maintain one token identity with multiple provenance observations if useful.

==================================================
9. DISCOVERY OBSERVATION
==================================================

Create a model representing a discovery observation.

Conceptually:

TokenDiscoveryObservation

containing:

- token identity
- network ID
- account ID if account-specific
- discovery source
- discovered timestamp
- reason
- metadata snapshot if available

Do not claim the observation proves ownership.

Do not claim it proves legitimacy.

==================================================
10. WHAT COUNTS AS DISCOVERY?
==================================================

For Phase 3.3, implement only safe discovery mechanisms that are practical with the current architecture.

The preferred mechanism is:

transaction/event-based discovery

using public blockchain information.

Do NOT scan the entire blockchain.

Do NOT scan every contract.

Do NOT scan every block from genesis.

Do NOT create a blockchain indexer.

Do NOT add an external indexing service.

If event-based discovery is not safely supportable with the current RPC architecture, implement the discovery interface and a controlled known-contract/user-added path, and explicitly document event scanning as deferred.

Do NOT invent an incomplete discovery system merely to satisfy the feature.

==================================================
11. ERC-20 TRANSFER EVENT
==================================================

If implementing on-chain discovery through logs, use the standard ERC-20:

Transfer(address,address,uint256)

event.

The event signature is:

Transfer(address,address,uint256)

Use the standard event topic.

Do NOT manually invent topic encoding.

Prefer viem's existing ABI/log utilities.

==================================================
12. ACCOUNT-SCOPED DISCOVERY
==================================================

Discovery should be tied to a wallet account where appropriate.

For example:

Wallet Account A

may discover token X.

Wallet Account B

may not have interacted with token X.

Do not assume all accounts share the same discovered-token set.

However, token identity itself remains:

network + contract.

Separate:

asset identity

from:

account discovery state.

==================================================
13. MULTI-NETWORK DISCOVERY
==================================================

Discovery must remain network-scoped.

The same contract address on:

Ethereum

and:

Base

must create separate asset identities.

Never merge them because:

symbol/name match.

==================================================
14. DISCOVERY LIMITS
==================================================

Discovery must be bounded.

Do not allow a single request to:

- scan unlimited blocks
- retrieve unlimited logs
- create unlimited token records
- consume unbounded memory

Introduce reasonable:

- block range limits
- result limits
- metadata lookup limits

Document the limits.

If a request exceeds the allowed range:

return a clear normalized error or require pagination/chunking.

Do NOT silently scan more than the requested/allowed scope.

==================================================
15. LOG DISCOVERY SAFETY
==================================================

If using eth_getLogs:

filter narrowly by:

- network
- account address
- Transfer event topic

Use appropriate indexed address topics.

Do not request the entire chain's Transfer events.

Do not use:

eth_getLogs

without bounded block ranges.

Do not automatically scan from block 0.

==================================================
16. FALSE POSITIVES
==================================================

A contract emitting a Transfer-shaped event does NOT automatically prove it is a legitimate ERC-20.

After discovering a candidate:

run the Phase 3.2 contract/metadata validation.

A candidate may be:

- discovered
- ERC-20-compatible
- metadata partial
- unverified

These states may coexist.

==================================================
17. ZERO BALANCE DISCOVERY
==================================================

Do not automatically hide a discovered token solely because its current balance is zero.

A user may have:

- previously held it
- sent it away
- received an event
- intentionally added it

However, do not automatically flood the asset list with every historical zero-balance token.

Separate:

discovered candidate

from:

visible portfolio asset.

Visibility policy belongs to the portfolio layer.

==================================================
18. VISIBILITY STATE
==================================================

Create a public token visibility model.

Possible values:

- visible
- hidden

This is NOT a security/trust decision.

Hidden means:

"Do not show this token in the user's primary asset view."

It does NOT mean:

"Token is malicious."

It does NOT delete the asset identity.

==================================================
19. USER INTENT
==================================================

User-added tokens represent explicit user intent.

Record provenance:

user_added

but do not automatically upgrade verification status.

For example:

User adds a contract claiming to be "USDT".

The engine may resolve:

name = USDT
symbol = USDT
decimals = 6

But verification remains:

unknown/unverified

unless trusted verification evidence exists.

==================================================
20. METADATA REFRESH

21. METADATA CHANGES
==================================================

FINAL PRINCIPLE
==================================================

WaveX must maintain this distinction:

TOKEN IDENTITY
    ↓
CONTRACT COMPATIBILITY
    ↓
METADATA
    ↓
DISCOVERY
    ↓
PROVENANCE
    ↓
VERIFICATION
    ↓

These are different layers.

Discovery means:
