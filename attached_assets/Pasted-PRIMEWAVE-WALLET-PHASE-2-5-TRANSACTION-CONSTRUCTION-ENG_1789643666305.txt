==================================================
PRODUCT SECURITY INVARIANT
==================================================

PrimeWave Wallet is strictly non-custodial.

Private keys and recovery phrases:
- MUST NEVER leave the user's device.
- MUST NEVER be sent to the backend.
- MUST NEVER be sent to RPC providers.
- MUST NEVER be logged.
- MUST NEVER be persisted outside the secure vault.
- MUST NEVER be exposed through transaction-construction APIs.
- MUST NEVER be required by this phase.

PHASE 2.5 MUST NOT:
- sign transactions
- broadcast transactions
- access private keys
- access recovery phrases
- unlock the secure vault
- create signatures
- call eth_sendRawTransaction
- add backend transaction APIs
- add token logic
- add swap logic
- add DApp logic
- add WalletConnect
- add transaction history
- add fiat pricing
- add UI screens

This is an UNSIGNED TRANSACTION CONSTRUCTION phase only.

PHASE 2.5 OBJECTIVE
==================================================

Build a UI-independent EVM Transaction Construction Engine.

Its responsibility is:

Transaction Intent
        ↓
Validation
        ↓
Network Context Validation
        ↓
Gas Estimation
        ↓

==================================================
2. TRANSACTION TYPES
==================================================

Support:

LEGACY

and

EIP1559

Use the fee information already provided by Phase 2.4.

For Legacy:

- gasPrice
- gasLimit

For EIP-1559:

- maxFeePerGas
- maxPriorityFeePerGas
- gasLimit

Do not create a fake fee model.

Do not silently convert one model into another.

The transaction object must explicitly state which fee model is being used.

If the existing fee engine determines that only Legacy is available, construct a Legacy transaction.

If EIP-1559 is available, use the appropriate EIP-1559 model according to the existing fee engine.

Do not introduce arbitrary gas multipliers or fee padding.

==================================================
3. VALIDATE NETWORK
==================================================

Every transaction must be bound to an explicit network.

Before constructing a transaction:

- verify the network exists
- verify it is enabled
- verify it is configured
- verify it is the currently selected active network
- verify the RPC chain ID matches the registry chain ID

The transaction chainId MUST come from the validated network context.

Never allow the caller to arbitrarily construct a transaction for a different chain than the active network.

If the active network changes during construction:

FAIL safely.

Return a normalized network-change error.

Do not silently rebuild using the new network.

PrimeWave's current Mainnet entry remains a placeholder until real Mainnet configuration is supplied.

Do NOT invent PrimeWave Mainnet RPC or chain values.

==================================================
4. VALIDATE FROM ADDRESS
==================================================

Validate:

- valid EVM address
- checksum normalization where appropriate
- transaction FROM must correspond to a known local wallet account

IMPORTANT:

This does NOT mean accessing the private key.

Use public wallet/account metadata only.

If the FROM address is not one of the locally available public wallet accounts:

reject construction.

Do not automatically substitute another account.

==================================================
5. VALIDATE TO ADDRESS
==================================================

For normal transactions:

- TO must be a valid EVM address.

Support generic contract destinations.

Do not assume every contract address is safe.

Do not attempt to determine whether a contract is malicious.

Do not add security claims that cannot be verified.

For native transfers, TO is required.

If contract creation is NOT already supported by the current architecture, do not introduce it in this phase.

Do not expand scope unnecessarily.

==================================================
6. VALIDATE VALUE
==================================================

Value must be represented safely as bigint internally.

Accept a deterministic blockchain-unit representation.

The engine must reject:

- negative values
- malformed numeric values
- unsafe JavaScript numbers
- NaN
- Infinity
- decimal strings where the expected input is base-unit quantity
- overflow conditions

Do not use parseFloat for blockchain amounts.

Do not use floating-point arithmetic.

If human-readable conversion is needed, use existing exact formatting utilities.

==================================================
7. VALIDATE DATA / CALLDATA
==================================================

Transaction data must:

- be a valid 0x-prefixed hexadecimal string
- contain only hexadecimal characters
- have valid byte structure

Normalize consistently.

For example:

0x

must represent empty calldata.

Reject malformed calldata.

Do not decode ABI.

Do not guess what calldata does.

Do not modify calldata.

==================================================
8. NONCE HANDLING
==================================================

If nonce is supplied:

- validate it as a safe non-negative bigint/integer representation
- use it exactly as supplied
- never silently modify it

If nonce is omitted:

retrieve the current transaction count using the existing Account State / RPC layer.

Use the appropriate existing RPC method.

The nonce must belong to the validated FROM address and active network.

Do not maintain a local nonce counter.

Do not persist nonce state.

Do not implement nonce replacement.

Do not implement speed-up transactions.

Do not implement cancellation transactions.

Those belong to a later phase.

==================================================
9. GAS ESTIMATION
==================================================

Use the existing Phase 2.4 Gas/Fee Engine.

Do not duplicate eth_estimateGas logic.

If gasLimit is explicitly supplied:

validate it.

If gasLimit is omitted:

estimate gas using:

- from
- to
- value
- data

Only public transaction information may be passed.

Never pass private key material.

Never sign anything.

Never broadcast anything.

Reject:

- zero gas estimates
- malformed estimates
- RPC estimation errors
- network changes during estimation

IMPORTANT:

Do not automatically add:
- 10%
- 20%
- 30%
- any hidden multiplier
- any hidden buffer

If future UX requires a buffer, it must be an explicit later design decision.

==================================================
10. FEE CONSTRUCTION
==================================================

Use Phase 2.4 Fee Engine.

For Legacy:

network fee =
gasLimit × gasPrice

For EIP-1559:

network fee estimate =
gasLimit × maxFeePerGas

Clearly label this as a maximum fee estimate rather than claiming it is the exact amount ultimately charged.

All calculations must use bigint.

No floating point.

No fiat conversion.

No price API.

No hidden markup.

No PrimeWave fee unless an explicit protocol fee exists in a future specification.

==================================================
11. TOTAL VALUE CALCULATION
==================================================

For a native currency transaction:

total maximum native amount required =
value + estimated/max network fee

Use bigint.

Never allow overflow.

The engine should provide enough information for future UI to show:

Amount
+
Maximum network fee
=
Maximum total required

Do not claim this is the final fee actually charged on-chain.

For contract calls with non-zero value, the same calculation applies.

==================================================
17. NETWORK RACE PROTECTION
==================================================

This is important.

A transaction must not be constructed using mixed network state.

Capture network context at the beginning:

- network ID
- chain ID
- active network
- relevant configuration identity

Before returning the final transaction:

verify that the active network has not changed.

If it changed:

reject with NETWORK_CHANGED.

Do not return a transaction built from stale network context.

Apply the same protection to nonce, gas estimation, and fee retrieval wherever practical.
