WAVEX — PHASE 6.1: SWAP ARCHITECTURE & QUOTE MODEL

We are now implementing Phase 6.1 of the WaveX wallet roadmap: Swap Architecture & Quote Model.

WaveX is a strictly non-custodial, MetaMask-like EVM wallet.

IMPORTANT DEVELOPMENT RULES

- Work ONLY on Phase 6.1.
- Do NOT implement a real swap provider yet.
- Do NOT call 0x, 1inch, LI.FI, Paraswap, Uniswap APIs, or any other external swap/quote API.
- Do NOT execute swaps.
- Do NOT sign transactions.
- Do NOT broadcast transactions.
- Do NOT add backend swap execution.
- Do NOT add fake/demo swap quotes.
- Do NOT fabricate exchange rates, prices, liquidity, routes, gas costs, or savings.
- Do NOT modify the existing transaction signing/broadcasting security boundaries.
- Do NOT introduce custodial behavior.
- Do NOT add persistent swap state yet.
- Do NOT build the final Swap UI yet.
- Reuse the existing WaveX architecture instead of duplicating blockchain/RPC/transaction logic.
- Keep the implementation small and modular because this project is being developed in Replit Free mode.
- Before changing code, inspect the existing architecture and identify the existing modules/interfaces that should be reused.

4. SWAP REQUEST MODEL

Create a provider-neutral model such as:

SwapQuoteRequest

It must contain at minimum:

accountId
senderAddress
networkId
chainId
sellAsset
buyAsset
sellAmount
slippage

Requirements:

- accountId identifies the local wallet account.
- senderAddress is public address only.
- networkId identifies the swap network.
- chainId is the expected EVM chain ID.
- sellAsset and buyAsset use existing network-scoped asset identity.
- sellAmount uses exact bigint/base-unit representation internally.
- slippage uses integer basis points.

Do NOT use floating-point arithmetic for token/base-unit amounts.


5. SAME-CHAIN ONLY

Phase 6.1 supports same-chain swaps only.

Require:

sellAsset.networkId === buyAsset.networkId

Reject cross-chain requests with a clear normalized error such as:

CROSS_CHAIN_SWAP_UNSUPPORTED

Do NOT implement bridging or cross-chain routing.


6. REQUEST VALIDATION

Create deterministic validation.

Reject:

- missing account ID
- invalid sender address
- unknown network
- disabled network
- unconfigured network
- chain mismatch
- invalid sell asset
- invalid buy asset
- same sell and buy asset
- zero sell amount
- negative sell amount
- malformed amount
- invalid slippage
- excessive slippage
- cross-chain asset pair
- unsupported asset type
- malformed contract address

Reuse existing network and asset validation systems wherever possible.

Do not duplicate validation unnecessarily.


7. SLIPPAGE MODEL

Represent slippage using integer basis points.

Examples:

50 bps = 0.50%
100 bps = 1.00%

Use:

slippageBps

Initial allowed range:

0 through 5000 bps

This represents:

0% through 50%

Reject values outside this range.

Do NOT silently modify user-provided slippage.

Do NOT automatically increase slippage.

Do NOT hide slippage inside provider logic.

9. EXACT AMOUNT SAFETY

Use bigint for token/base-unit monetary values.

This includes:

Never use JavaScript number for token/base-unit monetary values.

Never use floating-point arithmetic for token amounts.

10. EXPECTED VS MINIMUM RECEIVED

Keep these values separate:

expectedBuyAmount
minimumBuyAmount

They are NOT interchangeable.

minimumBuyAmount represents the minimum amount acceptable under the requested slippage protection.

Do not invent or calculate fake quote values during Phase 6.1.

The future provider integration will supply the quote data.


11. ROUTE MODEL

Create a provider-neutral route model that supports future multi-hop swaps.

For example:

SwapRoute
  hops[]

Each hop should support fields conceptually equivalent to:

inputAsset
outputAsset
poolOrVenue
protocol

The model must support:

Token A → Token B

and future:

Token A → Token X → Token B

Do not hardcode Uniswap-specific structures.

Do not assume every provider exposes identical route information.


12. PRICE IMPACT

Create a priceImpact field.

Do NOT fabricate price impact.

Do NOT infer price impact from incomplete information.

The architecture must allow:

when the provider does not provide reliable information.

Do not replace unknown with a fake zero.


13. FEE MODEL

Create a structured fee model that distinguishes:

Do not merge all fees into one unexplained number.

Do not introduce any WaveX markup.

WaveX must never silently add a fee to a provider quote.


14. GAS MODEL

The swap architecture must integrate conceptually with the existing Gas/Fee Engine from Phase 2.4.

Do NOT duplicate gas estimation logic.

A future provider may provide:

gas estimate
gas-related transaction information

However:

- Existing WaveX transaction construction remains authoritative.
- Provider output is untrusted.
- Final transaction data must be validated before signing.
- A quote is NOT an approved transaction.

Document this boundary.

17. QUOTE SERVICE

Create:

SwapQuoteService

Responsibilities:

1. Validate the swap request.
2. Validate account/network context.
3. Ensure same-chain operation.
4. Validate sell and buy asset identities.
5. Pass the validated request to the configured provider abstraction.
6. Validate provider response.
7. Reject malformed/untrusted quote data.
8. Return a normalized SwapQuote.

It must NOT:

- sign
- broadcast
- access private keys
- access mnemonic
- access SecureStore
- access PIN
- access biometrics
- modify wallet balances
- persist wallet secrets
- execute swaps.
