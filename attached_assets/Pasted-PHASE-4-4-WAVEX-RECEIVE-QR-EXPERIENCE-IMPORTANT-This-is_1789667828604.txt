PHASE 4.4 — WAVEX RECEIVE & QR EXPERIENCE

IMPORTANT:
This is a controlled UI/application phase.

PRODUCT NAME:
WAVEX

Do NOT display “PrimeWave Wallet” as the product name.
Do NOT display “by PrimeWave” in the WaveX product branding.

PrimeWave remains the ecosystem/network name where applicable.

==================================================
OBJECTIVE
==================================================

Implement the real WAVEX Receive experience.

The Receive flow must allow the user to:

- view their public wallet address
- view a QR code representing that public address
- copy the public address
- share the public address
- clearly see the currently selected network
- understand that the sender must use the correct network

Architecture:

WaveX Home
    ↓
Receive
    ↓
Public Account + Active Network
    ↓
Address / QR / Copy / Share

This is a receive-only/read-only feature.

==================================================
VISUAL REFERENCE
==================================================

Continue using the attached WAVEX Wallet UI reference image as the primary visual reference.

Follow its:

- dark futuristic aesthetic
- cyan / electric blue / violet accents
- premium cards
- subtle glow
- rounded surfaces
- thin borders
- typography hierarchy
- clean spacing
- polished mobile interaction

Use the existing centralized WaveX theme.

The reference is a VISUAL DESIGN REFERENCE only.

Do NOT copy example addresses, balances, token names, or fake functionality from it.

==================================================
1. RECEIVE SCREEN
==================================================

Create a dedicated Receive screen consistent with the WaveX design.

Suggested hierarchy:

Header
    WAVEX / Receive
    Back

Network context
    Current network

Main receive card
    QR code
    Account identity
    Public address

Actions
    Copy Address
    Share Address

Safety information
    Correct network warning

The screen should feel polished and production-ready.

==================================================
2. ACCOUNT CONTEXT
==================================================

Receive must use the currently authenticated/public account.

Display:

- account name where available
- account index
- shortened public address
- full public address

Example:

Account 1

0xf39F…2266

The underlying address must be the authoritative wallet address.

Do NOT hardcode an address.

Do NOT create another address-generation implementation.

==================================================
3. NETWORK CONTEXT
==================================================

Receive must clearly display the currently selected network.

Use the existing EvmNetwork model.

Display:

- network name
- native currency symbol where useful
- network status where appropriate

Example:

Ethereum
ETH

or:

PrimeWave Chain
Not configured

Do NOT invent PrimeWave production configuration.

==================================================
4. NETWORK SAFETY WARNING
==================================================

Include a clear warning that the sender must send using the correct network.

The wording should communicate:

“Only send assets using the selected network.”

Do not claim that all tokens can be safely received on every network.

Explain that an address may look identical across EVM networks, but the network still matters.

Keep the warning concise and understandable.

==================================================
5. QR CODE
==================================================

Implement actual QR code generation.

The QR must represent the PUBLIC wallet address.

It must NOT contain:

- private key
- mnemonic
- seed phrase
- PIN
- authentication credential
- signing capability
- secret data

Prefer a standard QR encoding containing the public EVM address.

Do NOT encode arbitrary sensitive wallet state.

==================================================
6. QR DEPENDENCY
==================================================

If a QR library is required:

- use a well-maintained library compatible with the current Expo/React Native environment
- pin the dependency to a compatible version
- avoid unnecessary native modules
- do not introduce a dependency that requires a native rebuild unless necessary
- document why the dependency is required

Before adding a dependency, inspect the existing package configuration and avoid duplicates.

Do not replace existing cryptographic dependencies.

Do not modify wallet cryptography.

==================================================
7. QR VISUAL QUALITY
==================================================

The QR code must:

- have sufficient contrast
- have adequate quiet-zone/margin
- remain square
- remain scannable at common mobile sizes
- not be obscured by decorative glow
- not place decorative elements inside the QR unless verified safe

The futuristic WaveX visual treatment must never reduce QR scan reliability.

Keep the QR itself clean and functional.

==================================================
8. COPY ADDRESS
==================================================

Implement:

“Copy Address”

Behavior:

1. Copy ONLY the public address.
2. Show clear confirmation.
3. Do not read clipboard contents.
4. Do not log clipboard contents.
5. Do not store clipboard contents.

Use the existing clipboard dependency/pattern introduced in Phase 4.3.

Do not duplicate clipboard architecture.

==================================================
9. SHARE ADDRESS
==================================================

Implement public-address sharing using the appropriate platform-compatible sharing mechanism.

Share only:

- public wallet address
- optionally a concise non-sensitive message containing the network name

Do NOT share:

- private key
- mnemonic
- seed
- PIN
- authentication state
- signing capability
- secrets

Example share content:

“WaveX address — Ethereum:
0x…”

Keep the shared content deterministic and user-controlled.

If native sharing is unavailable in Web Preview, provide a controlled fallback rather than claiming native sharing was tested.

==================================================
10. NETWORK + ADDRESS CONSISTENCY
==================================================

The Receive screen must use the same:

account + network

context as Home and Assets.

Do not generate a different address.

Do not create another account context.

Do not silently change networks.

If the network changes before or while Receive is open:

- update the displayed network
- ensure the warning reflects the new network
- ensure QR/address data remains consistent
- do not display stale network information

Because EVM addresses can remain the same across networks, the network label is still essential.

==================================================
11. UNCONFIGURED NETWORK
==================================================

If the selected network is unconfigured:

do NOT pretend the network is live.

Display its actual configured/unconfigured state.

The public EVM address may still be displayed because it is derived from the wallet account, but the UI must clearly communicate that the network itself is not configured for blockchain operations.

Do not invent balances or blockchain activity.

==================================================
12. DISABLED / INVALID NETWORK
==================================================

Handle:

- disabled network
- unavailable network
- invalid network context

using the existing network/error abstractions.

Do not silently fall back to another network.

Do not automatically switch networks.

==================================================
13. HOME INTEGRATION
==================================================

Wire the existing Home “Receive” action to the real Receive screen.

Do not leave Receive as “Coming Soon”.

Home → Receive must work.

Back → Home must work.

The bottom navigation may remain visible/hidden according to the established app shell, but do not redesign unrelated navigation.

==================================================
14. ASSETS INTEGRATION
==================================================

Do not create token-specific receive addresses.

Receive represents the current wallet account/address and selected network.

The screen should clearly communicate that the wallet address is the account's public EVM address.

Do not imply that a token has its own wallet address.

==================================================
15. QR SCANNER
==================================================

IMPORTANT:

DO NOT implement QR SCANNING in this phase.

This phase implements:

QR DISPLAY / GENERATION

only.

The existing Scan button may continue to show “Coming soon”.

QR scanning will be handled separately because it requires camera/native permissions and recipient parsing/security review.

==================================================
16. NO TRANSACTION LOGIC
==================================================

Do NOT implement:

- transaction construction
- gas estimation
- signing
- broadcasting
- transfers
- approvals
- permits
- transaction history

Receive is read-only.

Do not call:

- TransactionBuilder
- LocalSigner
- TransactionBroadcastEngine

==================================================
17. NO SECRET ACCESS
==================================================

The Receive UI MUST NOT access:

- mnemonic
- seed phrase
- private key
- PIN
- SecureStore
- SecureVault
- Keychain
- Keystore
- WalletAuthenticator
- LocalWalletEngine secret APIs
- signing capabilities
- authorization secrets

Only public account/network data may be consumed.

==================================================
18. CLIPBOARD SECURITY
==================================================

Only the public address may enter the clipboard.

The app must never:

- read clipboard contents
- log clipboard contents
- persist clipboard contents

Reuse the existing public-address copy implementation.
