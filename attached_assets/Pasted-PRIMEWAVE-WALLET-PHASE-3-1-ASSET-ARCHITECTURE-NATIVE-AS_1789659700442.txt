PRIMEWAVE WALLET — PHASE 3.1
ASSET ARCHITECTURE & NATIVE ASSET ENGINE

You are continuing development of PrimeWave Wallet.

This is Phase 3.1 ONLY.

Build the asset abstraction and native EVM asset engine.

DO NOT implement:
- ERC-20 tokens

Do not redesign the existing architecture.

==================================================
PRODUCT REQUIREMENTS
==================================================

PrimeWave Wallet is a non-custodial multi-chain EVM wallet.

V1 supports:

- PrimeWave Chain
- Ethereum
- BNB Chain
- Polygon
- Arbitrum
- Base
- Optimism
- future/custom EVM networks

The asset architecture must therefore NOT assume:

- ETH is always the native asset
- one network has one fixed symbol
- decimals are always 18
- one asset exists globally across all networks

Assets are network-scoped.

==================================================
PHASE 3.1 OBJECTIVE
==================================================

Create a clean asset architecture that can represent:

1. Native EVM assets
2. Future ERC-20 assets
3. Future NFTs / other asset classes

BUT IMPLEMENT ONLY NATIVE ASSETS IN THIS PHASE.

The architecture should allow later token support without redesigning the entire portfolio system.

==================================================
1. ASSET TYPE SYSTEM
==================================================

Create a strongly typed asset model.

At minimum establish:

AssetType

with:

- native
- fungible_token
- nft

Only `native` should be implemented functionally in Phase 3.1.

The other types may exist as architectural types if useful, but MUST NOT have incomplete functionality pretending to work.

==================================================
2. ASSET IDENTITY
==================================================

Create a stable asset identity model.

An asset must not be identified only by:

symbol

or:

name.

For native assets, identity should be network-scoped.

Conceptually:

AssetIdentity

- assetType
- networkId
- assetId

For a native asset:

assetId can be a canonical native identifier such as:

"native"

The architecture should make it impossible to accidentally treat:

ETH on Ethereum

as the same blockchain asset as:

ETH-like assets on another network.

Do not use symbol as the primary key.

==================================================
3. NATIVE ASSET MODEL
==================================================

Create a NativeAsset model containing at minimum:

- asset type
- stable asset ID
- network ID
- chain ID
- name
- symbol
- decimals
- native currency identifier
- enabled/availability state

Do not duplicate native currency information unnecessarily.

Prefer deriving the native asset metadata from the existing EvmNetwork registry where appropriate.

The network registry remains the source of truth for:

- native currency name
- native currency symbol
- native currency decimals

If the existing registry currently has the necessary metadata, reuse it.

If PrimeWave's final Mainnet native currency metadata is still placeholder/unconfigured, do NOT invent it.

==================================================
4. ASSET REGISTRY
==================================================

Create an AssetRegistry or equivalent abstraction.

Responsibilities:

- resolve native asset for a network
- resolve asset by stable identity
- validate asset/network relationship
- reject unsupported asset types
- prevent duplicate identities

Do NOT create a hardcoded global list like:

ETH
BNB
MATIC
ARB
BASE

Instead derive native assets from the network registry.

The architecture must support future networks without rewriting the asset engine.

==================================================
5. NETWORK-SCOPED ASSET RULE
==================================================

Every asset operation must carry network context.

Do not allow:

getBalance(address)

without knowing which network is intended.

Prefer:

getBalance(networkId, address)

or an equivalent strongly typed request.

This is important because the same EVM address can exist on multiple networks while representing different balances.

==================================================
6. NATIVE BALANCE ENGINE
==================================================

Create a UI-independent NativeAssetBalanceService.

It should retrieve the native asset balance using the existing:

EvmAccountStateService

Do NOT duplicate:

eth_getBalance

logic.

The service should return a structured balance model.

Conceptually:

NativeAssetBalance

- asset identity
- network ID
- chain ID
- account ID
- address
- raw balance as bigint
- decimals
- symbol
- exact display amount
- retrieval timestamp
- block context where available

The raw blockchain amount MUST remain bigint.

==================================================
7. EXACT AMOUNT REPRESENTATION
==================================================

Do not use JavaScript floating point for balances.

Examples that must remain exact:

1 wei
1000000000000000000 wei
123456789012345678901234567890 wei

Use bigint internally.

Human-readable formatting must use exact decimal conversion.

Do not use:

parseFloat
Number(balance)
toFixed on blockchain quantities
floating-point multiplication

for financial calculations.

==================================================
8. DISPLAY FORMATTING
==================================================

Create a safe exact amount formatter.

For example:

formatAssetAmount(rawAmount, decimals)

Requirements:

- deterministic
- no floating-point arithmetic
- handles zero
- handles very large values
- handles very small values
- handles arbitrary decimals
- preserves exactness internally
- supports trimming unnecessary trailing zeros for display

Examples conceptually:

1000000000000000000 / 18
→ "1"

1500000000000000000 / 18
→ "1.5"

1 / 18
→ "0.000000000000000001"

Do not round the underlying value.

If display precision is intentionally limited, make that a presentation-only operation and document it.

==================================================
9. PARSING HUMAN AMOUNTS
==================================================

Create a safe conversion utility for future transaction UI use.

Conceptually:

parseAssetAmount("1.5", 18)

→

1500000000000000000n

Requirements:

- exact decimal parsing
- no floating point
- reject negative amounts unless explicitly supported
- reject malformed decimals
- reject exponent notation
- reject NaN
- reject Infinity
- reject excessive decimal places
- reject overflow
- reject empty values

This utility must NOT be connected to sending yet.

It is only an asset arithmetic primitive.

==================================================
10. DECIMAL RULES
==================================================

Decimals are metadata.

Never assume:

18 decimals

for every native asset.

Use the network registry's configured decimals.

Validate:

- decimals is a non-negative integer
- reasonable bounds
- no malformed decimal metadata

Do not invent decimals for placeholder networks.

==================================================
11. NATIVE ASSET RESOLUTION
==================================================

Given a valid configured network:

resolveNativeAsset(networkId)

must return a deterministic NativeAsset.

For example:

Ethereum:
networkId = ethereum
chainId = 1
native symbol = ETH
decimals = configured value

BNB Chain:
networkId = bnb
chainId = 56
native symbol = BNB
decimals = configured value

Polygon:
networkId = polygon
chainId = 137
native symbol = configured native symbol
decimals = configured value

Do not hardcode these values if they already exist in the network registry.

==================================================
12. PRIMEWAVE PLACEHOLDER
==================================================

PrimeWave Mainnet remains unconfigured/placeholder until official configuration is supplied.

Therefore:

resolveNativeAsset(primewave-mainnet)

must follow the same configuration rules as the network registry.

Do not invent:

- PrimeWave chain ID
- PrimeWave RPC
- native symbol
- native decimals
- explorer

If the network is not configured:

reject native asset resolution.

==================================================
13. ACCOUNT OWNERSHIP
==================================================

Native balance retrieval must operate on public account information only.

It may accept:

- account ID
- public address

It must NOT require:

- private key
- mnemonic
- vault access
- PIN
- biometric authentication

Balance retrieval is read-only.

==================================================
14. ACTIVE NETWORK BEHAVIOR
==================================================

Do not silently assume the active network.

The caller must explicitly identify the network.

If the architecture chooses to support an active-network convenience method, it must:

- read the currently selected network
- reject if none is selected
- never silently switch networks

Do not create hidden network switching.

==================================================
15. NETWORK CONSISTENCY
==================================================

When retrieving a balance:

capture:

- network ID
- chain ID

before the operation.

Verify the relevant network context remains valid before returning the result.

If the active network changed during an active-network operation:

reject with the established network-change error.

For explicitly network-scoped operations, continue using the requested network context and do not silently switch it.

==================================================
16. STALE DATA
==================================================

Do not create a persistent balance cache in this phase.

Each retrieval should represent a fresh RPC-backed observation.

Include:

- retrieval timestamp
- latest known block context if already available

Do not claim the balance is real-time.

Do not poll continuously.

Do not create background balance refresh.

That belongs to the portfolio layer.

==================================================
17. BLOCK CONTEXT
==================================================

Where practical, associate the balance with the latest block context obtained by the existing account-state service.

Do not introduce duplicate block-number RPC calls if existing services already provide this information.

The result may include:

- block number
- block hash if available
- retrieval timestamp

This allows later portfolio systems to reason about stale observations.

==================================================
18. MULTI-ACCOUNT SUPPORT
==================================================

The asset engine must support multiple local wallet accounts.

Balance identity must include:

- account ID
- public address
- network ID
- asset identity

Do not assume account index 0.

Do not automatically choose the first account.

Do not persist a separate account balance database.

==================================================

Do not calculate:
