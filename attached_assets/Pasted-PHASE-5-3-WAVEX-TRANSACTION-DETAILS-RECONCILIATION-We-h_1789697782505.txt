PHASE 5.3 — WAVEX TRANSACTION DETAILS & RECONCILIATION

We have completed and approved:

- Phase 5.1 — Activity / Transaction History Architecture
- Phase 5.1A — Activity Presentation Model Amendment
- Phase 5.2 — WAVEX Activity UI

Current verified state:

- Full wallet suite: 212/212 tests passing
- TypeScript passing
- Static iOS and Android Expo builds passing
- Activity repository exists
- ActivityService exists
- ActivityReadModelService exists
- ActivityPresentationModel exists
- Asset-first Activity UI exists
- Network badge presentation exists
- Account/network/chain isolation exists
- Exact bigint quantities are enforced
- Existing broadcast and confirmation engines remain authoritative
- Activity row → transaction detail is currently only a placeholder

OBJECTIVE

Replace the Activity transaction-detail placeholder with a proper WAVEX Transaction Details experience.

Also establish the foundational reconciliation behavior needed to keep transaction status accurate.

The flow should become:

Activity
  ↓
Transaction Details
  ↓
Read-only transaction information
  ↓
Optional reconciliation / refresh
  ↓
Current known status

This phase is READ-ONLY from the blockchain perspective.

DO NOT add:

- Swap
- Swap execution
- Swap detection
- DApp / WalletConnect
- backend history
- external indexers
- price APIs
- notifications
- transaction replacement
- speed-up
- cancellation
- fee bumping

==================================================
1. CORE PRINCIPLE
==================================================

Transaction Details must clearly distinguish:

LOCAL TRANSACTION RECORD
UNSIGNED TRANSACTION
SIGNED TRANSACTION
BROADCASTED TRANSACTION
CONFIRMING TRANSACTION
CONFIRMED TRANSACTION
REVERTED TRANSACTION
FAILED TRANSACTION
UNKNOWN TRANSACTION

Never collapse these into a generic "success" state.

A transaction being:

SIGNED

does NOT mean:

BROADCASTED

A transaction being:

BROADCASTED

does NOT mean:

CONFIRMED

A transaction being:

UNKNOWN

does NOT mean:

FAILED

==================================================
2. DETAIL SCREEN
==================================================

Create:

src/components/TransactionDetailScreen.tsx
src/components/TransactionDetailScreen.logic.ts
src/components/tests/transaction-detail-screen.test.ts

Follow existing project architecture and naming conventions if an equivalent structure already exists.

The screen must consume the existing ActivityReadModelService / ActivityPresentationModel.

Do NOT duplicate activity data models.

Do NOT make UI code responsible for blockchain interpretation.

==================================================
3. NAVIGATION
==================================================

Activity row tap should navigate to Transaction Details.

Pass only:

- activity ID
- safe public context if required

Do NOT pass:

- private key
- mnemonic
- signing capability
- PIN
- biometric credentials
- SecureStore values
- wallet secrets

The detail screen must resolve the authoritative activity record through the Activity service/read model.

- dark futuristic background
- deep navy/black surfaces

- restrained glow
- premium rounded cards
- clean typography
- strong information hierarchy

The Activity screenshot remains the visual reference for the overall wallet experience.

The Transaction Details page should feel like the natural next screen after tapping an Activity row.

Do not create a separate design system.

Header:

Depending on activity type:

with:

"Transaction"

==================================================
7. STATUS
==================================================

Display the current transaction status prominently.

Supported states:

- Draft
- Signed
- Broadcasting
- Broadcasted
- Confirming
- Confirmed
- Reverted
- Failed
- Unknown

Use honest wording.

Examples:

"Signed locally — not broadcast"

"Broadcasted — awaiting confirmation"

"Confirming"

"Confirmed"

"Reverted"

"Broadcast failed"

"Status unknown"

Do not show:

"Successful"

unless the actual state is confirmed.

Do not show:

"Sent"

as proof of blockchain confirmation.

==================================================
8. STATUS EXPLANATIONS
==================================================

Where useful, provide concise explanations.

Example:

UNKNOWN:

"The broadcast result could not be established. Check the transaction on the network before attempting anything again."

Do NOT tell the user to rebroadcast automatically.

For reverted:

"The transaction was included on-chain but execution reverted."

For failed:

"The transaction did not reach confirmed on-chain execution."

Use the existing normalized error/state model where available.

Do not expose raw RPC errors.

==================================================

==================================================

Display:

FROM

- full sender address
- shortened address
- copy action

TO

- full recipient/contract address
- shortened address
- copy action

Use existing clipboard boundaries.

Never read clipboard contents.

Do not persist clipboard contents.

Do not label an address:

- safe
- trusted
- verified

unless explicit trusted metadata exists.

A valid EVM address is not proof that it is safe.

==================================================
10. TRANSACTION HASH
==================================================

If a blockchain transaction hash exists:

Display:

Transaction Hash

- shortened hash
- full hash accessible
- copy action

If no hash exists:

"Transaction hash not yet available"

Do not fabricate a hash.

For locally-created transactions before broadcast:

use the local transaction identity appropriately.

Do not pretend the local ID is an on-chain transaction hash.

- network name

- network icon/badge where available
- configured/unconfigured status

Do not infer network from:

- token symbol
- transaction hash

==================================================
18. BLOCK / CONFIRMATION INFORMATION
==================================================

For confirmed/reverted transactions where receipt data exists:

show:

- block number
- confirmation status
- confirmation count if reliably available

If confirmation count cannot be reliably established:

do not fabricate it.

A transaction with a receipt should still distinguish:

successful execution

from:

reverted execution.

==================================================
19. TIMESTAMP
==================================================

Display the appropriate transaction time.

Prefer authoritative blockchain-derived timestamp where available.

Otherwise use observation timestamp with appropriate semantics.

Do not label observation time as blockchain time.

The underlying model must preserve timestamp source.

==================================================
20. EXPLORER
==================================================

If the configured network provides a valid explorer transaction URL:

show:

"View on Explorer"

Use only validated configured explorer metadata.

Do not construct arbitrary explorer URLs.

Do not invent explorer URLs.

For placeholder/unconfigured networks:

do not display a fake explorer link.

The explorer action must not alter wallet state.

==================================================
21. RECONCILIATION
==================================================

Implement foundational read-only reconciliation for known transaction hashes.

Use the existing Phase 2.7 transaction lookup / confirmation architecture.

Do NOT create a second receipt polling engine.

When the detail screen is refreshed or reconciliation is explicitly requested:

For transactions with a known transaction hash:

- look up the transaction using the existing broadcast/lookup infrastructure
- if receipt exists, update activity status appropriately
- if receipt indicates successful execution, use confirmed
- if receipt indicates reverted execution, use reverted
- if transaction remains pending, preserve confirming/broadcasted state
- if status cannot be established, preserve unknown

Do NOT automatically rebroadcast.

Do NOT sign.

Do NOT modify transaction data.

==================================================
22. RECONCILIATION FOR UNKNOWN
==================================================

UNKNOWN must be treated carefully.

If a broadcast timed out:

UNKNOWN

does NOT mean:

FAILED.

The user may manually request reconciliation.

Use:

- transaction hash lookup
- receipt lookup
- existing confirmation engine

If the transaction is later found:

update the activity record.

If it is still not found:

remain UNKNOWN.

Do not automatically resubmit the signed transaction.

==================================================
23. RECONCILIATION BOUNDS
==================================================

Reconciliation must be bounded.

Do not create:

- infinite polling
- aggressive polling
- background polling loops
- automatic retry loops

A user-triggered refresh may perform a bounded read-only reconciliation.

Respect the existing Phase 2.7 timeout semantics.

==================================================
24. EXTERNAL TRANSACTIONS
==================================================

The detail architecture must support transactions discovered on-chain that were not created by WAVEX.

Such transactions may have:

- no localTransactionId
- transactionHash
- accountId
- networkId
- chainId
- blockchain-derived data
- provenance = blockchain_read

The UI should not imply:

"Sent from WAVEX"

unless provenance supports that claim.

Use neutral wording where origin is unknown.

==================================================
25. PROVENANCE DISPLAY
==================================================

Do not necessarily expose technical provenance directly to ordinary users.

However, preserve it internally.

Examples:

local_wallet
broadcast_engine
confirmation_engine
blockchain_read
external_indexer_future

The presentation model may use provenance to select appropriate wording.

Never use provenance to make unsupported security/trust claims.

28. REFRESH
==================================================

Possible states:

- Refresh
- Checking
- Updated
- No change
- Unable to reconcile

Do not hide network reads.

Do not make refresh trigger a broadcast.

Do not make refresh trigger signing.

==================================================
29. ACCOUNT / NETWORK ISOLATION
==================================================

The detail record must remain bound to:

- accountId
- sender/related account
- networkId
- chainId

If the account context changes:

- invalidate the current detail view
- do not display another account's activity

If the network context changes:

- the transaction detail remains tied to its original network
- do not reinterpret the transaction on the newly selected active network
- do not silently switch active network

Remember:

The Activity network filter and wallet active network are separate concepts.

==================================================
30. NO TRANSACTION MUTATION
==================================================

Transaction Details is READ-ONLY.

It must NOT:

- sign
- broadcast
- replace
- speed up
- cancel
- bump fees
- modify nonce
- modify recipient
- modify amount

The only blockchain operations allowed are public/read-only lookup/reconciliation.

==================================================
31. SECURITY BOUNDARY
==================================================

Transaction Details must never access:

- mnemonic
- private key
- SecureStore secrets
- PIN
- biometric credentials
- signing capability

Do not import:

- LocalSigner
- TransactionSigningFlow

Do not import or invoke:

- TransactionBroadcastEngine.broadcast()
- eth_sendRawTransaction

If reconciliation needs transaction lookup, use the existing read-only lookup method only.
